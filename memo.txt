・テーマタイトルの用途は？
フロントで表示される単なるテキストですか？
→TourOptionの分類・検索軸として使う項目です（公開前チェック必須項目にも含まれています）。フロントでの表示よりも「どのテーマのツアーか」を社内で分類するためのラベルに近いイメージです。ただし表示用に使う設計も排除されていないので、フロントに出す場合は単なるテキストとして使えます。

・「正式名称（英）」、「選択表示名」は商品名として多言語対応すれば大丈夫ですか？
→はい。
正式名称（英）：英語の固有の正式名称
選択表示名：自社サイトのTourOption選択UIに出す表示用の名前

・タグ／バッジのバッジってなんでしょうか？
→タグは検索やフィルタで使う分類ラベルで、バッジはTourOptionの選択カードに目立つように貼る視覚的なラベルです。

たとえばタグは「食体験」「自然」「歴史」のような内容で、管理画面の絞り込みや将来的なフロントのカテゴリ検索に使うイメージです。

バッジは「人気」「貸切」「午前発のみ」のような短い文言で、商品ページのTourOption選択エリアでそのOptionのカードに重ねて表示するラベルです。KlookやKKdayで商品の画像に「NEW」「ベストセラー」と貼ってあるあのイメージです。

ただ、初期でフロントのTourOption選択UIが具体的にどこまで作り込まれるかによって、バッジが実際に必要かどうかも変わってくると思います。フロント側のデザインが決まってから、タグとバッジを一本化するか分けるかを決めても遅くないかと思います。

時限式リソースの処理フロー（概念） 2026.06.16

時限式リソースの処理フロー（概念）を整理しました。
実装してみないと見えない部分もありますが、下記の流れで購入制限が可能かご意見いただけますと幸いです。

【要件】
・ガイドのリソースは今回の検討対象外
・複数の TourOption が同じリソースを共有 できる
・リソースは cooldown（再利用可能時間）経過後に復活 する

【管理画面】
・TourOptionマスター
https://design.unidemo.net/de/admin/tour-option-detail.html?tab=availability

・Resourceマスター
https://design.unidemo.net/de/admin/resource-detail.html?id=rm_04

【処理の流れ（概念）】
在庫テーブルinventoryテーブルは持たず、リソースマスターで保有数（totalQty）を設定
  ↓
予約リクエスト時に、受注テーブルからcooldownを考慮にいれた消費数を計算
  ↓
保有数、消費数、リクエスト数から受け入れ可能かどうか判定

①Deep側
予約リクエスト受信
  ↓
該当TourOptionの催行リソース設定を取得
※複数TourOptionがリソースを共有するケースあり
  ↓
各リソースについて受注テーブルから消費リソース数を集計
※同時刻〜再利用可能までの時間（cooldown）時間以内の予約で消費済みリソース数を集計
※キャンセルデータなどは集計対象外
  ↓
各リソースの残数 = 保有数（totalQty） - 消費済みリソース数

紐づけされている全リソースで（各リソースの残数 - 今回の予約リクエストのリソース数）>= 0 であれば → 受注OK
いずれかで リソース不足 → 受注NG

②OTA側との連携
・OTA側は webhook があるため、リアルタイムに受注データ取り込み可能
・OTAから予約確定通知を受信
・Deep側で在庫を再計算（①と同じロジック）
・必要に応じて OTA販売停止API を実行

【補足】
複数TourOptionがリソースを共有するケースで、在庫の競合判定は「同一時間帯の予約確定数」をリアルタイムで集計する必要がある。
現在の管理画面はマスターデータの定義まで（保有数・cooldown・消費数の設定）、実際の在庫チェックはバックエンドの予約システム側の実装になる。
設定項目に過不足がないかは、具体的なユースケースで検証が必要。
競合制御（ダブルブッキング防止）：バックエンド側で 排他制御（ロック） を検討する必要がある。

「今回の予約リクエストのリソース数」 の数え方
per_tour（催行固定）リソース → 1（人数に関係なく1消費）
per_person（人数割）リソース → 予約人数分（例：4人予約なら4消費）
この変換をバックエンドで行う。

【メリット】

→ 鉄道中心の用途ならコスパが良い

1リクエストあたり 0.05〜0.2円
（駅名検索／経路検索／運賃取得）

■ 合計イメージ

3. NAVITIME API
【メリット】
・とにかく高機能（徒歩・バス・タクシー・混雑・時刻表など）
・バスを本格的に扱う場合は NAVITIME 一択
・駅・バス停のオートコンプリート精度が高く、スマホ入力との相性が非常に良い

【デメリット】
・API が複雑で、実装コストが高い
・駅名検索の扱いが駅すぱあとより難しい
・レスポンスが重く、UI 側の実装も増える
→ NAVITIME は返ってくるデータ量が多く、構造も複雑なので、そのまま画面に出せず “整形・分解・マッピング” が必要になる。

【利用料金（目安）】
■ 基本料金（例）
月額固定費：数万円〜
→ 利用する API の種類で変動
→ 駅＋バス＋経路検索なら 3〜5万円/月 が多い

■ 従量課金（例）
1リクエストあたり 0.1〜0.3円
→ 地点検索（駅・バス停）
→ 経路検索（鉄道＋バス）

例：
ガイドさんが1日10回検索 × 100人
→ 1,000回/日 → 月3万回
→ 従量課金は 3,000〜9,000円/月 程度

■ 合計イメージ
月額 3〜6万円程度

※ 正確な金額は用途・規模で変わるので、問い合わせが必要。

TourOption登録について 2026.06.23

新規作成ボタン
  → デリートフラグオン（is_deleted = 1） で最小限のレコード挿入（名称はUUIDや仮称で自動設定）
  → 発行されたIDの編集ページへリダイレクト
  → ユーザーが編集・保存
  → バリデーション通過 → ステータスを任意の値に変更

懸念点：孤児レコード問題
ユーザーが仮挿入後にブラウザを閉じたり離脱した場合、下書き状態の空レコードが溜まります。定期的なクリーンアップジョブ（例：7日以上更新のない下書きを削除）はセットで考えておいた方がよいです。

提案：タブをグループ化して2階層にする
▼ 基本設定（1〜2タブ）  →  基本情報 / 提供条件
▼ 販売設定（2〜3タブ）  →  販売条件 / 販売期間・リソース
▼ コンテンツ（1タブ）   →  コンテンツ
▼ 運営管理（3タブ）     →  ツアー行程 / 運営・確認 / チャネル / 経費

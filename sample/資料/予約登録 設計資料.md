# 予約登録 設計資料（修正版）

## 1. この資料の目的

この資料は、DeepExperienceの新システムにおける「予約登録」の基本方針、データ構造、管理機能の設計方針と範囲を整理するための資料です。

初期MVPだけを定義する資料ではなく、今後の更新で将来フェーズの設計も追記していく親資料として扱います。  
そのため、本資料内で「初期MVP」と書く場合は、予約登録設計全体のうち、初期リリースで優先して実装・運用確認する範囲を指します。

ここでいう初期MVPは、単に予約情報を保存する機能ではなく、**発生した予約をツアー運営部が対応すべき「案件」として管理できる状態にするために、初期リリース時点で最低限そろえるべき業務・データ・管理機能のまとまり**を指します。

予約登録設計の目的は以下です。

- 自社サイト、OTA、問い合わせ、旅行会社 / 代理店などで発生した予約を一元的に管理する
- 予約を社内の案件として扱えるようにする
- 予約IDを付与し、後続業務の起点にする
- 商品・TourOption・商品条件スナップショットと予約を紐付ける
- ツアー日時、人数、ゲスト情報、集合情報、支払い状況などを確認できる
- 予約内容の不備、重複、変更履歴を確認できる
- 個人情報とガイド共有情報を分けて管理できる
- ガイド手配、催行回管理、変更・キャンセル対応へ渡せる状態にする

予約登録は、**予約・手配・催行・顧客対応の入口**となる基盤です。

---

## 2. 設計の基本方針

### 2-1. 初期MVPで実現したいこと

初期MVPでは、以下を実現できる状態を目指します。

- 発生した予約を社内の予約案件として登録できる
- 自社サイト予約、OTA予約、問い合わせ予約、旅行会社 / 代理店予約を同じ予約データ構造で管理できる
- 予約ごとに一意の予約IDを付与できる
- 外部予約番号・取込元システム予約IDと社内予約IDを紐付けられる
- 予約されたTourOptionを特定できる
- 予約時点の商品条件スナップショットを紐付けられる
- 予約変更時に、変更前後の商品条件スナップショットや重要項目の履歴を残せる
- 予約日時、ツアー日時、開始時間、人数、ゲスト情報を管理できる
- 集合場所、ピックアップ有無、ゲスト要望など、運営に必要な情報を確認できる
- 予約ステータスと運営確認ステータスを分けて管理できる
- データ不備、変更あり、キャンセル、重複疑いなどをフラグや履歴として管理できる
- 予約内容に不備や要確認事項がある場合に検知できる
- 重複予約の可能性を確認できる
- ガイド手配や催行回管理に渡すための最低限の情報を保持できる
- 変更・キャンセル・返金対応時に、元の予約情報を確認できる
- 将来的にBokun・OTA・自社サイト・会計システムとの連携に拡張しやすい構造にする

### 2-2. 初期MVPでやりすぎないこと

初期MVPでは、以下は原則として対象外、または簡易対応とします。

- 高度なリソース管理
- 複雑な催行回自動生成ロジック
- ガイド自動アサイン
- 顧客への自動メール・チャット配信
- OTAごとの完全な予約同期ロジック
- 決済処理そのもの
- 返金処理そのもの
- 請求書発行・会計連携の完全自動化
- 複雑な変更・キャンセルワークフロー
- 顧客マイページ上の高度な予約変更機能
- CSV / APIなどの技術的な取込方式の詳細管理
- AIによる予約内容の自動判断・自動対応

ただし、将来拡張できるように、データ構造としては拡張余地を残します。

### 2-3. 将来版・最終版の扱い

本資料では、初期MVPで実装する範囲だけでなく、将来フェーズで追加する可能性がある設計も追記していきます。  
初期MVPに含める項目と、将来フェーズとして残す項目は、各章で明示します。

## 4. データ構造の基本方針

初期MVPでは、予約登録のデータ構造を以下の **4つのコア一覧 + 8つの補助一覧** で整理します。

### 4-1. コア一覧

| 一覧 | 目的 | 主な内容 |
| --- | --- | --- |
| 予約一覧 | 予約案件の基本情報を管理する | 予約ID、予約元、予約日時、ツアー日時、ステータスなど |
| ゲスト・参加者情報一覧 | 予約者・参加者の情報を管理する | 氏名、メール、電話番号、国籍、言語、参加者情報など |
| 外部参照情報紐付け一覧 | 外部システム上の予約番号・取込元システム予約IDと社内予約IDを紐付ける | OTA予約番号、旅行会社管理番号、取込元システム予約ID、外部管理画面URLなど |
| 予約 × 催行回 紐付け一覧 | 予約を催行回に紐付ける | 予約ID、催行回ID、割当状態など |

### 4-2. 補助一覧

| 一覧 | 目的 | 主な内容 |
| --- | --- | --- |
| 予約取込ログ一覧 | 予約データがどこから、いつ取り込まれたかを管理する | 取込元システム、通知・取込方法、取込日時、処理結果、エラー内容など |
| 予約確認チェック一覧 | 予約内容に不備がないか確認する | 必須項目チェック、データ不備フラグ、確認者など |
| 重複チェックログ一覧 | 二重登録の可能性と判定結果を管理する | 類似予約、正予約ID、重複予約ID、判定結果、対応状況など |
| 予約変更履歴一覧 | 予約変更時の変更前後を管理する | 変更前後の商品条件スナップショット、日時、人数、TourOption、変更理由など |
| 支払い・料金サマリー一覧 | 予約に紐づく金額・支払い状況を参照する | 販売金額、通貨、支払い状況、決済元など |
| 個人情報・共有範囲管理一覧 | ゲスト情報の共有可否を管理する | 社内限定、ガイド共有可否、共有範囲、保持期間など |
| 予約メモ・参照情報一覧 | 予約ごとの補足情報を管理する | 社内メモ、ガイド共有メモ、施設予約確認書URL、問い合わせメールURLなど |
| 予約監査ログ一覧 | 登録・更新・変更履歴を管理する | 更新者、更新日、変更項目、変更理由など |

### 4-3. 基本的な親子関係

初期MVPでは、以下の関係を前提とします。

- 1つの予約は、必ず1つの予約IDを持つ
- 初期MVPでは、1予約 = 1TourOption = 1ツアー日時を基本とする
- 1つの予約は、予約時点の商品条件スナップショットIDを持つ
- 1つの予約は、0または複数の外部参照情報を持つ場合がある
- OTA予約では、外部予約番号または取込元システム予約IDを原則として持つ。B2B(旅行会社・法人)予約では外部予約番号は任意とし、可能な限り入力を推奨する
- 自社サイト予約・手動登録予約では、外部予約番号を持たない場合がある
- 1つの予約は、0または1つの催行回に紐付く
- 1つの催行回には、複数の予約が紐付く場合がある
- Private / Custom系は、原則として1予約 = 1催行回になりやすい
- Group系は、複数予約 = 1催行回になる場合がある

予約登録直後や確定待ちの予約であっても、TourOption・日時・人数などが明確で、既存または作成予定の催行回を特定できる場合は、催行回に紐付けてよいです。

一方で、TourOption・日時・人数・成立可否・重複疑いなどが未確定の場合は、催行回未紐付け状態を許容します。

そのため、催行回IDは常に必須ではなく、**未紐付け / 仮紐付け / 確定紐付けを分けて管理し、後続の催行回管理で確定紐付けできる構造**にします。

### 4-4. 将来拡張の考え方

初期MVPでは、1予約 = 1TourOption = 1ツアー日時を基本とします。

ただし将来的に、以下のようなケースに対応する場合は、上位概念として「注文」または「案件」を持ち、その配下に複数の予約明細を持てる構造へ拡張できるようにします。

| 将来ケース | 例 |
| --- | --- |
| カート購入 | ゲストが1回の購入で複数ツアーを同時予約する |
| パッケージ商品 | 2日間ツアーの中に複数のTourOptionが含まれる |
| 追加オプション | 通常ツアー + 着物レンタル + 送迎などをまとめる |
| B2B一括案件 | 旅行会社が複数日程・複数ツアーをまとめて依頼する |
| 同一決済内の複数商品 | 1回の支払いで複数の体験を購入する |

ただし、初期MVPでは「予約」と「注文」を混ぜず、**予約は1つのツアー実施案件として扱う**ことを優先します。

## 5. 予約情報

### 5-1. 予約情報の目的

予約情報MVPの目的は、発生した予約を社内の案件として登録し、ツアー運営部が後続対応できる状態にすることです。

ここで重要なのは、予約を単なる「売上データ」ではなく、**運営対応が必要な案件データ**として扱うことです。

予約情報は、以下の後続業務の起点になります。

- ガイド募集
- ガイドアサイン
- 催行回作成・紐付け
- 施設予約
- ゲスト連絡
- 予約変更
- キャンセル対応
- 返金判断
- レビュー管理
- トラブル対応

### 5-2. 初期MVPで管理すべき主な項目

#### 予約一覧

- 予約ID
- 予約コード
- 予約受付方式
- 予約元区分
- 販売チャネル
- 取込元システム
- 外部予約番号
- 取込元システム予約ID
- 予約作成日時
- 予約取込日時
- 予約確定日時
- ツアー日
- 開始時間
- 終了予定時間
- タイムゾーン
- TourOption ID
- TourOptionコード
- 商品ページID
- 商品ページ × TourOption 紐付けID
- 商品条件スナップショットID
- 予約ステータス
- 運営確認ステータス
- データ不備フラグ
- キャンセル対応要否フラグ
- 重複疑いフラグ
- 正予約ID（重複判定時）
- 催行回ID
- ガイド手配開始可否
- 予約確認期限
- 対応担当者
- 緊急度 / 優先度
- ゲスト連絡要否
- 施設予約要否
- 施設予約ステータス
- 登録者
- 最終更新者
- 最終更新日時
- 社内メモ

### 5-3. 予約IDの基本方針

予約登録設計では、外部予約番号とは別に、Deep側の社内予約IDを付与します。

理由は以下です。

- OTAごとに予約番号の形式が違う
- Bokun経由で取得する場合でも、OTA予約番号とBokun上の管理番号が異なる場合がある
- 手動登録予約には外部予約番号がない場合がある
- 社内業務では、共通の予約IDが必要になる
- 変更・キャンセル・返金・レビュー管理の基準IDが必要になる

例：

> BK-YYMMDD-XXXXX

YYMMDD部は予約受付日（予約を受け付けた日）を表します。通常はシステム登録日と同日ですが、登録が遅れた場合は実際に予約を受け付けた日を用います。連番（XXXXX）は日付ごとに独立して採番します。

ただし、ID形式の詳細はエンジニア側で実装しやすい形式に調整してよいです。

重要なのは、**外部予約番号ではなく、Deep側の予約IDを業務上の主キーにすること**です。

### 5-4. 予約作成日時・予約取込日時・予約確定日時

予約登録設計では、「予約作成日時」「予約取込日時」「予約確定日時」を分けて管理します。

| 項目 | 意味 |
| --- | --- |
| 予約作成日時 | 予約元システムまたは社内運用上で、予約が発生した日時 |
| 予約取込日時 | その予約データがDeepの自社システムに登録・同期された日時 |
| 予約確定日時 | 予約として成立し、運営対応対象になった日時 |

`確定予約` は、予約として成立していることを意味します。  
支払い済みであることは意味しません。支払い状態は、支払いステータスで別管理します。

## 6. 予約元・チャネル管理

### 6-1. 予約元・チャネル管理の目的

予約元・チャネル管理MVPの目的は、予約がどこから発生したかを明確にし、チャネルごとの確認・対応・集計ができるようにすることです。

同じツアー商品でも、予約元によって以下が異なる場合があります。

- 予約番号
- 通知・取込方法
- 予約内容の項目
- キャンセルポリシー
- 決済受領者
- ゲストへの連絡方法
- 変更・キャンセルの受付方法
- 返金処理の担当先

そのため、予約登録時点で予約元を必ず管理します。

初期MVPでは、チャネル別キャンセルポリシーそのものを商品管理側で高度にルール化せず、商品条件スナップショットから参照できるキャンセル条件を基本とします。  
OTA / B2Bなどで実際のキャンセル条件が異なる場合は、予約側のスナップショット、チャネル別メモ、または外部参照情報として保持し、運営確認対象にします。

予約元区分は「どこから予約が来たか」を表す項目です。  
予約が即時に確定するのか、Deep側の確認後に確定するのかは、予約元区分ではなく予約受付方式で管理します。

### 6-2. 予約受付方式

初期MVPでは、予約受付方式を以下の2つに整理します。

| 予約受付方式 | 内容 |
| --- | --- |
| 即時確定予約 | 予約登録時点で予約が確定し、運営対応対象になる予約 |
| リクエスト予約 | 予約希望または予約リクエストは存在するが、Deep側・ガイド・施設・リソースなどの確認後に確定する予約 |

問い合わせや旅行会社 / 代理店経由の予約は、受付方式ではなく予約元区分として扱います。  
たとえば「問い合わせ × リクエスト予約」「旅行会社 / 代理店 × リクエスト予約」のように組み合わせて管理します。

### 6-3. 予約元区分

初期MVPでは、予約元区分を以下のように整理します。

| 予約元区分 | 内容 |
| --- | --- |
| 自社サイト | 自社サイト上でゲストが直接予約した予約 |
| OTA | Viator、GetYourGuide、Klook、Airbnbなどから発生した予約 |
| 問い合わせ | メール、フォーム、WhatsAppなどから手動登録する予約 |
| 旅行会社 / 代理店 | B2B経由で発生した予約 |
| 法人 | 法人案件として発生した予約 |
| その他 | 上記に当てはまらない予約 |

### 6-4. Bokunの扱い

Bokunは、多くの場合「予約が発生した場所」ではなく、**予約を取得・管理・同期する中継システム**です。

そのため、Bokun経由で取得したOTA予約であっても、予約元区分は「OTA」とし、販売チャネルに「Viator / GetYourGuide / Klook」などを設定します。

Bokunは予約元ではなく、**取込元システム**または**外部管理システム**として管理します。

### 6-5. 初期MVPで管理すべき項目

| 項目 | 内容 |
| --- | --- |
| 予約受付方式 | 即時確定予約、リクエスト予約 |
| 予約元区分 | 自社サイト、OTA、問い合わせ、旅行会社 / 代理店、法人など |
| 販売チャネル | Viator、GetYourGuide、Klook、Airbnb、自社サイトなど |
| 取込元システム | Bokun、自社サイト、手動登録など |
| 通知・取込方法 | API、CSV、メール、Webhook、手動など。初期は取込ログ側の任意項目 |
| 外部予約番号 | OTAや旅行会社側の予約番号 |
| 外部商品ID | OTAやBokun上の商品ID。初期は任意 |
| 外部TourOption ID | OTAやBokun上のOption ID。Deep側TourOptionとの対応に使う。初期は任意 |
| 取込元システム予約ID | Bokunなど取込元システム上の予約ID。初期は任意 |
| 予約作成日時 | 予約元で予約が発生・成立した日時 |
| 予約取込日時 | Deepシステムに登録・同期された日時 |
| チャネル別メモ | チャネル固有の注意点 |

### 6-6. 予約取込ログとの違い

外部参照情報紐付けは、元予約を識別するための情報です。  
予約取込ログは、予約データがいつ・どの処理で取り込まれたかを確認するための処理ログです。

| 区分 | 目的 |
| --- | --- |
| 外部参照情報紐付け | 外部予約番号・取込元システム予約ID・外部管理画面URLなどから元予約を特定する |
| 予約取込ログ | 取込処理の成功・失敗・エラー内容を確認する |

## 7. 外部参照情報紐付け

### 7-1. 外部参照情報紐付けの目的

外部参照情報紐付けMVPの目的は、OTA・旅行会社・代理店など外部側の予約番号や、Bokunなど取込元システム上の予約IDと、Deep側の予約IDを紐付けることです。

外部参照情報を管理することで、以下が可能になります。

- OTA管理画面で元予約を確認する
- 旅行会社からの問い合わせに対応する
- 予約変更・キャンセル時に元予約を特定する
- 重複予約の検知に使う
- 売上・チャネル別集計に使う
- Bokunなど外部管理システムとの照合に使う

### 7-2. 初期MVPで管理すべき項目

| 項目 | 内容 | 初期MVPでの扱い |
| --- | --- | --- |
| Deep予約ID | 社内業務上の主キー | 必須 |
| 外部予約番号 | OTA・旅行会社側の予約番号 | OTAは原則必須。B2B(旅行会社・法人)は任意(可能な限り入力を推奨) |
| 予約元区分 | 自社サイト、OTA、問い合わせなど | 必須 |
| 販売チャネル | Viator、GYG、Klook、自社サイトなど | 必須 |
| 取込元システム | Bokun、自社サイト、手動登録など | 必須または任意 |
| 取込元システム予約ID | Bokunなど取込元システム上の予約ID | 任意 |
| 外部管理画面URL | 元予約を確認するためのリンク | 任意 |
| 備考 | 補足情報 | 任意 |

### 7-3. Bokun予約IDの扱い

初期MVPでは、Bokun予約IDを必須項目にはしません。

Deep側の予約管理における主キーはDeep予約IDであり、Bokun予約IDは業務上の主キーではないためです。

ただし、Bokunを日常業務で予約確認に使う場合や、Bokun上の予約と照合する必要がある場合に備えて、**取込元システム予約ID**として任意で持てるようにします。

## 8. 商品・TourOption紐付け

### 8-1. 商品・TourOption紐付けの目的

商品・TourOption紐付けMVPの目的は、予約された商品がDeep側の商品管理上のどのTourOptionに該当するかを特定することです。

予約登録時点でTourOptionを特定できないと、後続業務に支障が出ます。

### 8-2. 初期MVPで管理すべき項目

| 項目 | 内容 |
| --- | --- |
| TourOption ID | Deep側の商品TourOptionを特定するシステム内部ID。商品管理側で自動生成される |
| TourOptionコード | Deep側の商品TourOptionを業務上識別する不変コード。社内管理、原価表、外部データ照合、表示・検索に使う |
| テーマタイトル | TourOptionレコードの任意項目。予約データ上は必須ではなく、商品条件スナップショットから参照可能 |
| 商品ページID | 自社サイト上の商品ページ。自社予約の場合に使用 |
| 商品ページ × TourOption 紐付けID | どの商品ページ経由のTourOptionかを示すID。自社予約の場合に使用 |
| 商品条件スナップショットID | 予約時点の商品条件一式を参照するID。必須 |
| 外部商品ID | OTA / Bokun上の商品ID。初期は任意 |
| 外部TourOption ID | OTA / Bokun上のOption ID。Deep側TourOptionとの対応に使う。初期は任意 |
| 商品名スナップショット | 予約時点で表示されていた商品名。商品条件スナップショットから参照可能だが、一覧表示・外部予約確認用に任意または自動保存で保持 |
| TourOption名スナップショット | 予約時点で表示されていたTourOption名。商品条件スナップショットから参照可能だが、一覧表示・外部予約確認用に任意または自動保存で保持 |

### 8-3. 初期MVPでの管理方針

初期MVPでは、予約データに以下を持たせることを必須にします。

- TourOption ID
- TourOptionコード
- 商品条件スナップショットID
- 外部予約の場合は、外部商品IDまたは外部商品名

商品名スナップショットとTourOption名スナップショットは、商品条件スナップショットIDから参照できる情報です。  
そのため必須項目ではなく、予約一覧表示や外部予約との照合をしやすくするための冗長データとして、任意または自動保存で保持します。

自動マッピングできない場合は、データ不備フラグを立て、運営が手動でTourOptionを選択します。

## 9. 商品条件スナップショット紐付け

### 9-1. 商品条件スナップショット紐付けの目的

商品条件スナップショット紐付けMVPの目的は、予約時点でお客様に提示していた商品条件を後から確認できるようにすることです。

予約後に商品情報が更新された場合でも、既存予約については、予約時点の商品条件を確認できる必要があります。

### 9-2. 初期MVPでの管理方針

初期MVPでは、予約登録時にTourOption ID（TourOptionバージョン）を解決し、それを基に予約時点スナップショット（商品条件スナップショット）を生成・紐付けます。

ここでいうTourOption IDは、提供内容（行程・集合解散・所要時間・含む物・定員/最少催行人数）の実体改訂のたびに発行されるTourOptionバージョンを一意に特定する内部主キーです。TourOptionコードは商品系統の不変識別子であり、TourOptionバージョンが変わってもコードは同一のまま重複しうるため、束ね鍵にはTourOption ID（TourOptionバージョン）を用います（コード一致ではなくTourOptionバージョン一致）。

予約が束ね鍵として保持するのはTourOption ID（TourOptionバージョン）です。商品条件スナップショットIDは、金額・販売条件・キャンセルポリシーを予約時点で再現するための予約時点スナップショット参照であり、束ね鍵には用いません。予約はTourOption ID（TourOptionバージョン）と商品条件スナップショットID（予約時点スナップショット）の両方を保持します。

> 注：束ね鍵に「提供内容ハッシュ」は不採用です。束ね鍵はTourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語の完全一致で構成します。

基本方針は以下です。

- 予約登録（TourOptionバージョン解決）時点で、TourOptionコードから該当TourOptionの**現在のTourOptionバージョンのTourOption ID**を取得し、予約をそのTourOption ID（TourOptionバージョン）にピン留めする
- 取得したTourOption ID（TourOptionバージョン）を基に、予約時点スナップショット（商品条件スナップショット）を生成し、予約データへ商品条件スナップショットIDとして紐付ける
- 予約が保持する束ね鍵はTourOption ID（TourOptionバージョン）であり、商品条件スナップショットIDは金額・ポリシー再現専用とする
- 商品更新（新TourOptionバージョン発行）後も、既存予約のTourOption ID（TourOptionバージョン）および商品条件スナップショットIDは変更しない（TourOptionバージョン固定。変更・キャンセルでも書き換えない）
- 予約変更により商品条件が変わる場合は、変更前後の商品条件スナップショットIDを予約変更履歴に残す（ただしTourOption ID（TourOptionバージョン）は据え置く）
- 現在のTourOptionバージョンのTourOption IDまたは商品条件スナップショットが取得できない場合は、データ不備フラグを立てる

#### 9-2-0. TourOptionバージョン固定のピン留め時点（TourOptionバージョン解決時点）

予約をTourOption ID（TourOptionバージョン）にピン留めする時点は、予約成立の経路によって異なります。いずれの経路でも、一度ピン留めしたTourOptionバージョンはその後の変更・キャンセルで書き換えません（TourOptionバージョン固定）。

| 予約元区分・受付方式 | TourOptionバージョン解決（ピン留め）時点 |
| --- | --- |
| 自社サイト（即時確定予約） | 予約成立時点で即時に現在のTourOptionバージョンのTourOption IDへピン留め |
| OTA（Bokun等経由の取込） | Deepシステムへの予約取込時点でTourOptionバージョン解決し、その時点の現在のTourOptionバージョンのTourOption IDへピン留め |
| リクエスト予約（自社・問い合わせ・B2B等） | リクエスト確定（予約成立）時点でTourOptionバージョン解決し、現在のTourOptionバージョンのTourOption IDへピン留め |

リクエスト予約は、リクエスト受付時点ではなく**確定時点**の現在のTourOptionバージョンでピン留めします。受付から確定までの間に新TourOptionバージョンが発行された場合は、確定時点の現在のTourOptionバージョンが適用されます。

### 9-2-1. 商品ページURLの自動判定

予約登録時に、ゲストが見ていた商品ページのURLを自動判定し、商品条件スナップショットの商品ページURLとして保存します。

| 予約元区分 | URL判定方法 |
| --- | --- |
| 自社サイト | 商品ページID → 自社サイト商品ページレコードのURLを自動取得 |
| OTA | TourOption ID × チャネルID → チャネル別掲載URLレコードを参照して取得 |
| 問い合わせ / 旅行会社 / 法人 | URLなし（取得対象外） |

取得したURLは、商品条件スナップショット.商品ページURLとして保存し、担当ガイドの案件詳細画面に表示します。

**アラートルール**：予約元区分がOTAである場合に、該当チャネル × TourOptionの組み合わせでチャネル別掲載URLレコードが未設定のときは、運営画面に以下のアラートを表示します。

> 「このチャネルのTourOption掲載URLが未設定です。商品管理 > チャネル別掲載URLから設定してください」

アラートは運営確認対象として記録しますが、予約の登録そのものはブロックしません。

### 9-2-2. OTA取込時のTourOptionバージョン決定ロジック

OTA予約（Bokun等経由）の取込では、外部側のID情報からDeep側のTourOption ID（TourOptionバージョン）を以下の2段階で解決します。

1. **外部ID → コード解決**：外部TourOption ID（OTA / Bokun上のOption ID）を、対応表からDeep側のTourOptionコードへ解決する
2. **コード → 現在のTourOptionバージョン解決**：解決したTourOptionコードから、取込時点の現在のTourOptionバージョンのTourOption IDを取得し、予約をそのTourOptionバージョンへピン留めする

いずれの段でも解決できない場合（外部IDの対応が未設定、または現在のTourOptionバージョンが取得できない）は、データ不備フラグを立て、運営が手動でTourOption（TourOptionバージョン）を選択します。

予約データには、TourOptionバージョンがどの根拠で確定したかを示す**TourOptionバージョン確定根拠**を保持します。

| TourOptionバージョン確定根拠 | 内容 |
| --- | --- |
| 自社確定 | 自社サイト予約など、Deep側で確実にTourOptionバージョンを解決できたもの |
| OTA推定 | OTA取込で外部ID→コード→現在のTourOptionバージョンの自動解決によりTourOptionバージョンを決定したもの |
| 手動選択 | 自動解決できず、運営が手動でTourOption（TourOptionバージョン）を選択したもの |

### 9-2-3. TourOptionバージョン・データ不備フラグの細分

TourOptionバージョン解決に関わるデータ不備は、原因の切り分けと運営対応を明確にするため、以下に細分して管理します。

| データ不備フラグ | 内容・運営対応 |
| --- | --- |
| TourOptionマッピング未確定 | 外部ID→コード解決が失敗（外部TourOption IDの対応未設定など）。運営が手動でTourOptionを選択 |
| TourOptionバージョン未確定（現在のTourOptionバージョン取得失敗） | コード→現在のTourOptionバージョン解決が失敗（公開中のTourOptionバージョン＝現在のTourOptionバージョンの取得失敗）。運営が手動でTourOption（TourOptionバージョン）を選択し、TourOptionバージョン確定根拠を「手動選択」とする |
| 商品条件スナップショット生成失敗 | TourOption ID（TourOptionバージョン）は確定したが、予約時点スナップショット（商品条件スナップショット）の生成・紐付けに失敗。再生成を運営確認対象とする |

「TourOptionバージョン未確定（現在のTourOptionバージョン取得失敗）」は、束ね鍵となるTourOption ID（TourOptionバージョン）が確定できていない状態であり、催行回への束ね・ガイド手配の前に必ず解消します。

なお、予約登録画面ではMVP割り切りとして、②TourOptionバージョン未確定（現在のTourOptionバージョン取得失敗）と③商品条件スナップショット生成失敗を1状態（取得成功 / 失敗）としてまとめて扱います（①TourOptionマッピング未確定を含む細分の管理はデータ不備フラグ側で行う）。

### 9-3. 管理項目例

- 予約ID
- TourOption ID
- TourOptionコード
- 商品条件スナップショットID
- 商品条件スナップショット番号
- 商品条件スナップショット適用日時
- 予約時点の商品名スナップショット（任意または自動保存）
- 予約時点のTourOption名スナップショット（任意または自動保存）
- 予約時点の集合場所
- 予約時点のキャンセルポリシーID
- 予約時点の販売価格
- 商品ページURL（ゲストが見ていたページURL。自社サイトは自動取得、OTAはチャネル別掲載URLレコードから取得）
- TourOptionバージョン確定根拠（自社確定 / OTA推定 / 手動選択）
- 商品条件スナップショット取得結果
- 商品条件スナップショット取得エラー内容

TourOption IDは束ね鍵（TourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語）として、商品条件スナップショットIDは金額・ポリシー再現専用の予約時点スナップショット参照として保持します。

予約時点の販売価格は商品条件スナップショットから参照できる基準価格として扱います。  
割引、OTA販売額、B2B個別条件などを反映した予約ごとの実販売金額は、支払い・料金サマリーで管理します。

### 10-1. ゲスト・参加者情報の目的

ゲスト・参加者情報MVPの目的は、予約者および参加者に関する情報を管理し、ツアー運営部や担当ガイドが必要な情報を確認できるようにすることです。

## 11. 個人情報・ガイド共有管理

### 11-1. 個人情報・ガイド共有管理の目的

個人情報・ガイド共有管理MVPの目的は、予約に含まれる個人情報や配慮事項を、必要な範囲で安全に扱うことです。

予約者名、メールアドレス、電話番号、国籍、食事制限、アレルギー、移動補助の有無などは、社内運用上必要な情報ですが、すべてを担当ガイドへ共有すべきとは限りません。

そのため、初期MVPでも以下を分けて管理します。

- 社内限定情報
- 担当ガイドに共有してよい情報
- 担当ガイドに必ず共有すべき情報
- 外部URLやメモに記載しない方がよい情報

### 11-2. 初期MVPで管理すべき項目

| 項目 | 内容 |
| --- | --- |
| ガイド共有可否 | ガイドに共有してよい情報か |
| ガイド共有メモ | ガイドに伝えるべき要点 |
| 社内メモ（ガイド非公開） | 運営部だけで確認する情報 |
| 個人情報区分 | 連絡先、健康・配慮情報、支払い関連など |
| 共有範囲 | 社内のみ、担当ガイドまで、外部パートナーまでなど |
| 情報保持期間メモ | 不要になった後の扱いに関するメモ |
| 閲覧制限要否 | アクセス制御が必要か |

### 11-3. 初期MVPでの管理方針

高度な権限管理は初期MVPでは対象外でも、少なくとも以下は実現します。

- 社内メモとガイド共有メモを分ける
- ガイド共有してよい情報だけを確認できる状態にする
- アレルギーや移動補助など、催行に必要な配慮事項はガイド共有対象として明示する
- 支払い情報、内部判断、返金交渉メモなどは原則として社内限定にする
- 外部管理画面URLや自由記述メモに個人情報を書きすぎない運用を前提にする

## 13. 予約ステータス設計

### 13-1. 予約ステータス

初期MVPでは、予約そのものの状態として以下のステータスを持たせます。

**ツアー実施前ステータス**

| ステータス | 意味 |
| --- | --- |
| 確定待ち | 予約希望または予約リクエストは存在するが、Deep側・ガイド・施設・リソースなどの確認が完了しておらず、確定予約として扱わない状態 |
| 確定予約 | 予約として確定し、運営対応対象になっている状態 |
| キャンセル済み | 予約がキャンセルされた状態。ゲスト側の二重予約による片方のキャンセルもこのステータスで管理し、重複疑いフラグと正予約IDを紐付ける |
| 無効 | 運営側の誤登録により、業務対象外とする状態 |

**ツアー実施後ステータス**

| ステータス | 意味 |
| --- | --- |
| Completed | ゲストがツアーに参加し完了した状態 |
| No-show | ゲストが当日現れなかった状態。予約はキャンセルされていない |
| Guide_No-show | ガイドが当日現れなかった状態。Deep側の責任。全額返金・再催行対応が発生する |
| Incompleted | ゲストがツアーを途中で離脱・未完了となった状態 |

`確定予約` は、支払い済みを意味しません。  
支払い状態は、支払いステータスで別管理します。

No-show・Guide_No-show・Incompletedは、予約がキャンセルされていないにもかかわらずツアーが正常完了しなかったケースであり、キャンセル済みとは別管理とします。

`リクエスト予約` は予約受付方式であり、`確定待ち` は予約ステータスです。  
たとえば、リクエスト予約として受け付けた予約は、Deep側の確認が完了するまで予約ステータスを `確定待ち` として管理し、受けられることが確認できたら `確定予約` に変更します。

予約受付方式と初期ステータスの基本対応は以下とします。

| 予約受付方式 | 初期の予約ステータス | 補足 |
| --- | --- | --- |
| 即時確定予約 | 確定予約 | 予約登録時点で運営対応対象にする |
| リクエスト予約 | 確定待ち | Deep側・ガイド・施設・リソースなどの確認後に確定予約へ変更する |

### 13-2. 予約フラグ

予約ステータスとは別に、以下のフラグを管理します。

| フラグ | 意味 |
| --- | --- |
| データ不備フラグ | 予約データに不備・確認事項がある（TourOptionマッピング失敗・必須項目未入力など）。システムが自動付与。手動で立てるボタンは設けず、運営は確認済み解除のみ。詳細は§14-3・§9-2-3 |
| キャンセル対応要否フラグ | キャンセル処理やキャンセル確認が必要 |
| 重複疑いフラグ | 重複登録の可能性がある |
| ゲスト連絡要否フラグ | ゲストへの確認連絡が必要 |
| 施設予約要否フラグ | 施設予約や外部確認が必要 |

`データ不備` や `変更あり` は、予約ステータスではなく、フラグまたは変更履歴として管理します。

### 13-3. 運営確認ステータス

予約ステータスとは別に、ツアー運営部の確認状態を管理します。

| ステータス | 意味 |
| --- | --- |
| 未確認 | 予約登録後、まだ運営が確認していない |
| 確認中 | 内容確認中 |
| 確認済み | 必要情報の確認が完了している |
| 要対応 | 追加対応が必要 |
| 対応完了 | 必要対応が完了している |

### 13-4. ステータス設計の基本方針

予約ステータスと運営確認ステータスは分けて管理します。

理由は、予約としては「確定」していても、運営上は「要確認」の場合があるためです。

重複が判明した場合の予約ステータスは、重複の原因によって使い分けます。

| 重複の原因 | 予約ステータス | 補足 |
| --- | --- | --- |
| ゲスト側の二重予約 | キャンセル済み | キャンセルポリシーの適用・返金を検討する。重複疑いフラグと正予約IDを紐付けて管理する |
| 運営側の誤登録 | 無効 | ポリシー不適用。内部処理のみ |

## 14. 予約確認チェック

### 14-1. 予約確認チェックの目的

予約確認チェックMVPの目的は、登録された予約が後続業務に進める状態かどうかを確認することです。

初期MVPでは、予約登録時または予約取込後に、必要情報がそろっているかを確認できる状態を目指します。

### 14-2. 予約確認チェック項目

初期MVPでは、以下を予約確認チェック項目とします。

| チェック項目 | 対象 |
| --- | --- |
| 予約IDが付与されている | 予約 |
| 予約元区分が設定されている | 予約 |
| 販売チャネルが設定されている | 予約 |
| 外部予約の場合、外部予約番号または取込元システム予約IDが登録されている | 外部予約 |
| 予約作成日時が設定されている | 予約 |
| 予約取込日時が設定されている | 予約 |
| ツアー日が設定されている | 予約 |
| 開始時間が設定されている | 予約 |
| TourOption IDが紐付いている | 商品 |
| TourOptionコードが紐付いている | 商品 |
| 商品条件スナップショットIDが紐付いている | 商品 |
| 参加者人数が設定されている | 参加者 |
| 予約者名が設定されている | ゲスト |
| 連絡先が設定されている | ゲスト |
| 集合場所またはピックアップ情報が確認できる | 集合情報 |
| キャンセルポリシーを参照できる | 商品条件スナップショット |
| 支払い状況を確認できる | 支払いサマリー |
| 重複疑いがない、または確認済みである | 重複チェック |
| ガイド共有メモと社内メモ（ガイド非公開）が分かれている | 個人情報・共有範囲 |
| ガイド手配に必要な情報がそろっている | 後続連携 |

### 14-3. 初期MVPでの管理方針

初期MVPでは、予約確認チェックは厳密な承認ワークフローではなく、確認補助機能として扱います。

- 未入力項目を表示する
- データ不備項目を一覧化する
- データ不備フラグはシステムが不備（必須項目未入力・TourOptionマッピング失敗など）を自動検知して自動付与する（手動でフラグを立てるボタンは設けない）
- 運営は内容を確認のうえ、データ不備フラグを「確認済み」にして解除できる
- 確認者・確認日時を記録する

予約確認チェックが完了していない予約でも、緊急対応のために後続業務へ進められる場合はあります。  
ただし、その場合も「データ不備（未確認）」状態を残し、対応漏れを防ぐ設計にします。

## 15. 重複チェック

### 15-1. 重複チェックの目的

重複チェックMVPの目的は、同じ予約が複数回登録されることを防ぐことです。

### 15-2. 重複判定に使う主な項目

| 項目 | 内容 |
| --- | --- |
| 外部予約番号 | 同一外部予約番号があるか |
| 取込元システム予約ID | Bokunなど取込元システム上の予約IDが一致するか |
| 予約者メールアドレス | 同じメールアドレスか |
| 予約者名 | 同じ氏名か |
| ツアー日 | 同じツアー日か |
| 開始時間 | 同じ開始時間か |
| TourOption ID | 同じTourOptionか |
| TourOptionコード | 同じ商品コードか |
| 参加者人数 | 同じ人数か |
| 販売チャネル | 同じチャネルか |

### 15-3. 重複判定後に管理すべき項目

重複と判断した場合は、どちらを正予約としたかを残します。重複側の予約は、原因に応じてキャンセル済みまたは無効にします。

| 項目 | 内容 |
| --- | --- |
| 正予約ID | 業務上有効な予約 |
| 重複予約ID | キャンセル済みまたは無効にした予約 |
| 判定者 | 重複判定した担当者 |
| 判定日時 | 判定した日時 |
| 判定結果 | 重複、別予約、要追加確認など |
| 判定理由 | 重複と判断した理由 |
| 処理理由 | キャンセル済みまたは無効にした理由（ゲスト二重予約 / 運営誤登録など） |

### 15-4. 初期MVPでの管理方針

初期MVPでは、完全自動判定ではなく、以下のような簡易チェックで十分です。

- 外部予約番号が一致する場合は重複として扱う
- 取込元システム予約IDが一致する場合は重複疑いとして表示する
- メールアドレス、ツアー日、開始時間、TourOptionが一致する場合は重複疑いとして表示する
- 重複疑い予約は、運営が確認して「別予約」または「重複」と判断する
- 重複と判断された予約は、正予約IDを紐付けたうえで、原因に応じてステータスを設定する
  - ゲスト側の二重予約：キャンセル済み（キャンセルポリシー・返金の適用を確認する）
  - 運営側の誤登録：無効（ポリシー不適用、内部処理のみ）

## 16. 予約変更履歴

### 16-1. 予約変更履歴の目的

予約変更履歴MVPの目的は、予約内容が変更された場合に、変更前後の重要情報を確認できるようにすることです。

予約変更では、ツアー日、開始時間、人数、TourOption、商品条件スナップショット、価格、キャンセルポリシーなどが変わる可能性があります。  
そのため、現在の予約情報だけでなく、変更前後の状態を履歴として残します。

### 16-2. 初期MVPで履歴を残すべき変更

- ツアー日
- 開始時間
- 人数
- TourOption ID
- TourOptionコード
- 商品条件スナップショットID
- 商品名・TourOption名スナップショット
- 集合場所
- ピックアップ情報
- 販売価格
- キャンセルポリシー
- 予約ステータス
- 支払いステータス
- 催行回ID
- ガイド手配に影響する情報

### 16-3. 管理項目例

- 予約変更履歴ID
- 予約ID
- 変更種別
- 変更前の商品条件スナップショットID
- 変更後の商品条件スナップショットID
- 変更前の値
- 変更後の値
- 変更理由
- 変更受付元
- 変更者
- 変更日時
- ゲスト連絡要否
- ガイド連絡要否
- 催行回再配置要否

### 16-4. 予約変更履歴と監査ログの違い

予約変更履歴は、業務上意味のある変更イベントを管理するものです。

一方で、監査ログは、誰がいつどの項目を更新したかを確認するためのシステム上の更新記録です。

| 区分 | 目的 | 例 |
| --- | --- | --- |
| 予約変更履歴 | 予約内容の変更前後を業務上確認する | 日程変更、人数変更、TourOption変更、商品条件スナップショット変更 |
| 監査ログ | 更新者・更新日時・変更項目を確認する | ステータス更新、メモ更新、担当者変更 |

## 17. 催行回連携

### 17-1. 催行回連携の目的

催行回連携MVPの目的は、登録された予約を催行回管理・ガイド手配へ渡せる状態にすることです。

初期MVPでは、催行回そのものの高度な管理までは行わず、**予約がどの催行回に紐付くか、または催行回作成対象かを判断できる状態**を目指します。

### 17-2. 予約と催行回の関係

| パターン | 説明 |
| --- | --- |
| Private / Custom | 原則として1予約 = 1催行回になりやすい |
| Group | 複数予約が1つの催行回に紐付く場合がある |
| 問い合わせ経由の予約 | 確定後に催行回作成対象になる |
| 確定待ち | 催行回への仮紐付けまたは未紐付けで管理する |

### 17-3. 初期MVPで管理すべき項目

- 予約ID
- 催行回ID
- 催行回紐付けステータス
- 未紐付け / 仮紐付け / 確定紐付け
- 紐付け日時
- 紐付け者
- 紐付け理由
- 再配置要否
- ガイド手配開始可否
- 催行回作成対象フラグ

### 17-4. ガイド手配開始可否の判断基準

初期MVPでは、以下がそろっていればガイド手配開始可能と判断できます。

- 予約ステータスが確定予約である
- ツアー日・開始時間が設定されている
- TourOption IDが設定されている
- TourOptionコードが設定されている
- 商品条件スナップショットIDが設定されている
- 参加人数が設定されている
- 集合場所またはピックアップ情報が確認できる
- 食事制限・アレルギー・特別配慮事項が確認されている
- ガイド共有メモに必要情報が整理されている
- 催行回に紐付いている、または催行回作成対象になっている
- 重複疑いがない、または重複確認済みである

### 17-5. 初期MVPでの管理方針

初期MVPでは、以下を実現できれば十分です。

- 予約が催行回に紐付いているか確認できる
- 催行回未紐付けの予約を一覧で確認できる
- Groupツアーでは、複数予約が同じ催行回に紐付く構造にする
- Private / Customでは、予約登録後に催行回作成対象にできる
- ガイド手配へ渡せる状態か確認できる

高度な催行回作成・再配置・リソース管理は、予約登録の初期フェーズではなく、リソース管理・催行回設計側で扱います。

## 18. 支払い・料金サマリー

### 18-1. 支払い・料金サマリーの目的

支払い・料金サマリーMVPの目的は、予約に関する金額・支払い状態を運営上確認できるようにすることです。

ただし、初期MVPでは、決済処理そのものや会計処理までは対象外とします。

### 18-2. 初期MVPで管理すべき項目

| 項目 | 内容 |
| --- | --- |
| 予約ID | 対象予約 |
| 販売金額 | ゲストが支払う、または支払った予約ごとの実販売金額。商品管理側の基準販売価格とは分けて扱う |
| 通貨 | JPY、USDなど |
| 支払いステータス | 未払い / Partially Paid / 支払い済み / 支払い不要 / 部分返金済み / 全額返金済み ／ チャージバック/係争（Chargeback / Disputed）／ ペナルティ適用（Penalty Applied）／ 要確認。値の正本は運営管理画面設計資料§2-1。**予約登録時点は4値（未払い / 支払い済み / 支払い不要 / 要確認）のみ選択可とし、正式9値へは登録後に更新可**（返金・係争・分割入金系は入金照合・返金処理等を経て付与） |
| 決済受領者 | ゲストの支払いを受け取る主体。Deep、OTA、旅行会社、代理店など |
| 決済元 | Stripe、OTA、銀行振込など |
| 決済ID | Stripe IDなど、外部決済ID。初期は任意 |
| チャネル手数料メモ | 初期はメモまたは参照管理 |
| 返金有無 | 返金が発生したか |
| 返金ステータス | 未処理 / 完了 / 不要 / OTA返金済み(Deep対応不要) / 要確認 / 特別対応中。値の正本は運営管理画面設計資料§2-1 |
| 料金メモ | 金額に関する補足 |

### 18-3. 初期MVPでの管理方針

初期MVPでは、支払い情報は「参照情報」として扱います。

商品・販売設計側の価格はTourOption単位の基準販売価格を管理し、予約登録側では予約ごとの実販売金額を参照・確認します。  
外部予約では、OTA / B2B側の販売額や手数料条件を必要に応じて料金メモまたは外部参照情報で補足します。

予約ステータスとは分けて、以下を確認できるようにします。

- 支払い済みか確認できる
- 決済受領者が分かる
- 販売金額が分かる
- 通貨が分かる
- 返金が発生しているか確認できる
- 決済元の外部IDを確認できる

## 19. メモ・参照情報・監査ログ

### 19-1. メモ管理の目的

メモ管理の目的は、予約案件ごとの運営上の注意点や、ゲスト対応履歴を残せるようにすることです。

### 19-2. 初期MVPで管理すべきメモ項目

- 社内メモ
- ゲスト要望
- ガイド共有メモ
- 施設予約メモ
- 支払い・返金メモ
- チャネル別注意事項
- トラブル対応メモ
- 変更・キャンセルに関するメモ

社内メモとガイド共有メモは、必ず分けて管理します。

### 19-3. 参照情報管理

初期MVPでは、以下のような参照情報を任意で管理できると望ましいです。

- 問い合わせメールURL
- Google Drive資料URL
- 施設予約確認書URL
- 請求書URL
- その他参考資料URL

URLは初期MVPでは必須項目にはしません。

OTA予約詳細URLやBokun予約詳細URLなど、元予約を特定するためのURLは、外部参照情報として管理します。  
この節の参照情報は、予約対応に関わる補足資料や関連ドキュメントを対象にします。

### 19-4. 監査ログ

予約監査ログMVPの目的は、予約情報の登録・更新履歴を残し、誰がいつ何を変更したかを確認できるようにすることです。

予約変更履歴が「日程変更」「人数変更」などの業務イベントを管理するのに対し、監査ログはシステム上の更新記録を管理します。

管理項目例：

- 監査ログID
- 予約ID
- 対象項目
- 変更前の値
- 変更後の値
- 更新者
- 更新日時
- 変更理由
- 社内メモ

初期MVPでは、すべての項目について差分を厳密に保存する必要はありません。  
ただし、ツアー日、開始時間、人数、TourOption、商品条件スナップショット、予約ステータス、キャンセル状態、支払いステータス、催行回ID、ガイド手配に影響する情報は履歴を残すことが望ましいです。

## 20. 初期フェーズで必要な画面・機能

予約一覧・予約詳細の画面要件の正本は「運営管理画面設計資料」および現行の管理画面HTMLとし、本章はそれを補完する位置づけとします。  
本章の項目のうち、正本に存在しない差分項目は将来フェーズとします。

### 20-1. 予約一覧画面

目的：登録された予約案件を一覧で確認する。

必要機能（初期フェーズ）：

- 予約一覧表示
- 予約ID表示
- 予約元・チャネル表示
- ツアー日・開始時間表示
- 商品名・TourOption名表示

## 21. 初期フェーズの対象外または後回しにするもの

初期MVPでは、以下は後回しでもよいと考えます。

| 項目 | 理由 |
| --- | --- |
| 高度なリソース管理 | リソース管理・催行回設計側で整理するため |
| 自動催行回生成の複雑なロジック | Group / Private / Customで条件が異なり、初期工数が大きいため |
| ガイド自動アサイン | ガイド管理・アサインMVP側で整理するため |
| 顧客向けマイページの高度な変更機能 | 予約変更MVP側で扱うため |
| OTAごとの完全同期 | チャネルごとの仕様差が大きいため |
| CSV / APIなどの技術的な取込方式の詳細管理 | 初期は業務上の予約管理を優先するため |
| 取込元システム予約IDの必須管理 | Deep予約IDを主キーにし、Bokunなど取込元システム上の予約IDは任意参照で足りるため |
| 外部管理画面URLの必須管理 | 外部予約番号や取込元システム予約IDがあれば元予約を検索できるため |
| 決済実行 | 決済MVPまたは外部決済サービス側で扱うため |
| 自動返金 | 返金・キャンセルMVP側で扱うため |
| 会計・請求書の完全連携 | 経理・会計MVP側で扱うため |
| 顧客コミュニケーション自動化 | CRM / メッセージ配信MVP側で扱うため |
| 高度な権限管理 | 初期は社内メモ（ガイド非公開）とガイド共有メモの分離を優先するため |
| AIによる予約内容自動判断 | 初期は手動確認を前提にするため |

## 23. まとめ

予約登録設計は、以下を実現するための基盤です。

- 発生した予約を社内の案件として管理する
- 自社サイト、OTA、問い合わせ、旅行会社 / 代理店など複数経路の予約を一元管理する
- 外部予約番号・取込元システム予約IDとDeep側予約IDを紐付ける
- Deep側予約IDを予約管理の主キーにする
- 予約されたTourOptionを特定する
- 予約時点の商品条件スナップショットを保持する
- 予約変更時に、変更前後の商品条件スナップショットや重要情報を履歴として残す
- ゲスト情報・参加者情報・人数情報を管理する
- 個人情報とガイド共有情報を分けて管理する
- ツアー日・開始時間・集合場所・ピックアップ情報を管理する
- 予約ステータスと運営確認ステータスを分けて管理する
- データ不備や変更ありをステータスではなくフラグ・履歴として管理する
- 不備・確認事項を可視化する
- 重複予約を防ぐ
- 予約を未紐付け / 仮紐付け / 確定紐付けとして催行回管理へ渡せる状態にする
- 支払い・料金情報を参照できるようにする
- 予約変更・キャンセル・返金・トラブル対応時に元情報を確認できるようにする

初期MVPでは、すべての予約関連業務を最初から自動化するのではなく、**Deepが発生した予約を正しく案件化し、ツアー運営部が後続対応できる状態を作ること**を優先します。

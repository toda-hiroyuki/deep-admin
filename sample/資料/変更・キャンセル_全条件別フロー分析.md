# 変更・キャンセル 全条件別フロー分析

本資料は「変更・キャンセル設計資料」「変更・キャンセル ユースケース一覧」の補足として、業務フロー・システム処理フローが変わる条件の全組み合わせを網羅する。

---

## 1. フローを変える条件軸

| 軸 | 値 | 影響する処理 |
|---|---|---|
| **A: 処理種別** | 日時変更 / 人数増員 / 人数減員 / 全件キャンセル | すべて |
| **B: 販売チャネル** | 自社サイト直販 / OTA経由 | 差額・返金処理に影響 |
| **C: ツアー種別** | プライベートツアー / グループツアー | 催行回の扱いに影響 |
| **D: 旧催行回に別の予約が残るか** | 残る（1件以上）/ 残らない（0件になる） | C=グループの場合のみ分岐。C=プライベートは常に0件（1催行回=1予約の原則） |
| **E: 商品条件スナップショット差額** | 差額なし / 差額あり | 主に日時変更で分岐。価格改定・割引等で予約時点と現時点の価格が異なる場合。**価格差額のみを指し、TourOptionバージョン（TourOption ID）の切替・引き直しは含まない（TourOptionバージョン固定）。差額＝同一コードの現在のTourOptionバージョン価格 vs 予約時点スナップショット価格** |
| **F: 発生元区分** | ゲスト都合 / 運営都合 / OTA経由（第三者都合） | 全件キャンセルで主に分岐。キャンセル料・返金ルールに影響 |
| **G: キャンセルポリシー期限** | 無料キャンセル期限内 / 有料キャンセル期限後 | 人数減員・全件キャンセル（ゲスト都合）で分岐 |
| **H: 予約ステータス** | 確定待ち / 確定予約 | 全件キャンセルのみ分岐。確定待ちはキャンセル料なし |

## 2. 日時変更

### 2-1. 条件と全パターン

| # | チャネル | ツアー種別 | 旧催行回に別予約 | 商品差額 |
|---|---|---|---|---|
| 日1 | 直販 | プライベート | （常に0件） | なし |
| 日2 | 直販 | プライベート | （常に0件） | あり |
| 日3 | OTA | プライベート | （常に0件） | なし |
| 日4 | OTA | プライベート | （常に0件） | あり |
| 日5 | 直販 | グループ | 残る（1件以上） | なし |
| 日6 | 直販 | グループ | 残る（1件以上） | あり |
| 日7 | OTA | グループ | 残る（1件以上） | なし |
| 日8 | OTA | グループ | 残る（1件以上） | あり |
| 日9 | 直販 | グループ | 0件になる | なし |
| 日10 | 直販 | グループ | 0件になる | あり |
| 日11 | OTA | グループ | 0件になる | なし |
| 日12 | OTA | グループ | 0件になる | あり |

### 2-2. 業務フロー（運営担当者の操作）

```
1. 対象予約を開く
2. キャンセルポリシーの期限を確認（期限ゲート。詳細は§8-1）
   ※ 期限ゲートはゲスト都合の日時変更に適用する。運営都合（天候・ガイド都合等）の日時変更は対象外として手順3へ進む
   ├─ [G: 無料キャンセル期限内] → 日時変更可能。手順3へ
   └─ [G: 有料キャンセル期限後] → 日時変更は受け付けない。「キャンセル料が発生するキャンセル扱い」として案内し§5-4へ移行。例外的に運営判断で承認する場合は例外承認を記録してフロー継続
3. TourOptionの「日程変更可否」を確認
   └─ 不可の場合: 例外承認の要否を判断。承認するなら記録してフロー継続
4. 発生元区分・変更理由を入力
5. 変更後の日時を入力
6. 現時点のTourOption価格を確認（予約時点の販売価格と照合）
   ├─ [E: 差額なし] → 差額なしを記録して手順7へ
   └─ [E: 差額あり] → 差額対応方針（追加請求 / 差額返金 / 変更なし）を選択・記録
7. 新日時でのリソース空きを確認（上限チェック）
   └─ 空きなし → 変更不可として記録。ゲストに連絡し別日時を検討
8. [グループ] 新日時で紐付け可能な催行回を確認
   └─ 適切な催行回なし → 新規催行回を作成してから紐付け
9. 変更を承認・実行
```

### 2-3. システム処理フロー（実行時）

**共通処理（全パターン）**
```
- 予約のツアー日・開始時間を更新（差額対応方針に応じて販売金額も更新）
- 旧日時のリソース消費を解放
- 新日時のリソースを確保
- 再手配要否フラグ = ON、変更理由区分 = 「日時変更」
- 変更・キャンセル履歴を保存
```

**[C: プライベートツアー]** ← 常にD=0件扱い
```
- 旧催行回を「Cancelled（中止）」に更新
- 旧催行回のガイド手配ステータスを「キャンセル」・通知要否フラグ = ON
- 新日時の催行回を自動生成・即「確定紐付け」（インライン新規催行回は予約のTourOption ID（固定TourOptionバージョン）を継承して生成。現時点の最新のTourOptionバージョンではない）
```

**[C: グループツアー × D: 旧催行回に別予約が残る]**
```
- 旧催行回から当該予約を解除 → 旧催行回の現在人数を更新
- 旧催行回は存続（有効予約1件以上のため無効化しない）
- 旧催行回のガイド手配は維持（再手配要否フラグON）
- 新催行回に仮紐付け（または新規催行回を作成して割り当て。インライン新規催行回は予約のTourOption ID（固定TourOptionバージョン）を継承して生成）
```

**[C: グループツアー × D: 0件になる]**
```
- 旧催行回から当該予約を解除 → 有効予約0件 → 旧催行回を自動的に「Cancelled（中止）」に更新
- 旧催行回のガイド手配ステータスを「キャンセル」・通知要否フラグ = ON
- 新催行回に仮紐付け（または新規催行回を作成して割り当て。インライン新規催行回は予約のTourOption ID（固定TourOptionバージョン）を継承して生成）
```

### 2-4. 処理後の自動更新・差額処理

**[B: 直販 × E: 差額なし]**
```
- チャネル手数料・決済手数料を自動再計算（差額は0のため実質変化なし）
```

**[B: 直販 × E: 差額あり × 対応方針=追加請求]**
```
- 追加請求レコードを作成・支払い管理側で請求処理
- チャネル手数料・決済手数料を差額分で再計算
```

**[B: 直販 × E: 差額あり × 対応方針=差額返金]**
```
- 返金レコードを作成・返金ステータス「未処理」
- チャネル手数料・決済手数料を差額分で再計算
```

**[B: 直販 × E: 差額あり × 対応方針=変更なし]**
```
- 販売金額はそのまま維持。記録のみ
```

**[B: OTA × E: 差額なし]**
```
- Deep側の金額処理なし
```

**[B: OTA × E: 差額あり]**
```
- 差額はOTAが次回定期振込時に調整。Deep側の処理なし
- 差額があることをメモに記録
```

## 3. 人数増員

### 3-1. 条件と全パターン

| # | チャネル | ツアー種別 | 定員・リソース状況 |
|---|---|---|---|
| 増1 | 直販 | プライベート | リソース内（通常） |
| 増2 | OTA | プライベート | リソース内（通常） |
| 増3 | 直販 | グループ | 定員内・リソース内（通常） |
| 増4 | OTA | グループ | 定員内・リソース内（通常） |
| 増5 | 直販/OTA | プライベート/グループ | リソース上限超過（処理不可） |
| 増6 | 直販/OTA | グループ | 催行回定員超過（不可 / 分割 / 特例拡張） |

> **注意**: 増5（リソース上限超過＝ハード）はメインフローに進めない。増6（催行回定員超過＝ソフト）は、別催行回への分割、または特例承認による定員拡張（ソフト上限のみ。リソース上限は免除しない＝§4-9）でメインフローに復帰しうる。チャネルの差は返金処理がないため影響しない。

### 3-2. 業務フロー

```
1. 増員依頼を受ける（ゲスト / OTA経由）
2. 変更後の参加人数を入力
3. [価格確認] 変更後人数のTiered Pricingを確認し、追加請求額を算出・確認
4. 追加人数分のリソースに空きがあるか確認（上限チェック）
   └─ 空きなし → 増員不可として記録（代替フロー増5）
5. [グループ] 催行回の定員（最大人数）を超えないか確認
   └─ 超過 → 増員不可 / 別催行回へ分割 / 特例承認で当該催行回の定員のみ拡張して受入（代替フロー増6）
      ※ 特例拡張はソフト上限（定員）のみ。リソース上限（ハード）は免除せず手順4で別途ゲートする（リソース管理・催行回設計資料 §4-9）
6. 増員を承認・実行
```

### 3-3. システム処理フロー

**共通処理（全パターン）**
```
- 予約の参加人数を更新
- 販売金額を更新（変更後人数 × Tiered Price後の単価）
- 追加請求額を記録（変更後合計金額 − 元の販売金額）
- 追加人数分のリソースを確保
- 催行回の現在人数を加算
- 再手配要否フラグ = ON、変更理由区分 = 「増員」
- 変更履歴を保存（Tiered Price算出根拠・追加請求額を含む）
```

**処理後自動更新（共通）**
```
- 販売金額増分・チャネル手数料・ゲスト立替経費（増員人数分を加算）を自動再計算
```

**[B: 直販]**
```
- 決済手数料を自動再計算（増員分の追加請求に新たな手数料）
- 追加請求額を支払い管理側で請求処理
```

**[B: OTA]**
```
- 増員分の追加請求はOTAが次回定期振込時に調整。Deep側の処理なし
- 決済手数料の再計算なし
```

## 4. 人数減員（部分キャンセル）

### 4-1. 条件と全パターン

| # | チャネル | ツアー種別 | キャンセル期限 |
|---|---|---|---|
| 減1 | 直販 | プライベート | 無料期限内 |
| 減2 | 直販 | プライベート | 有料期限後 |
| 減3 | OTA | プライベート | 無料期限内 |
| 減4 | OTA | プライベート | 有料期限後 |
| 減5 | 直販 | グループ | 無料期限内 |
| 減6 | 直販 | グループ | 有料期限後 |
| 減7 | OTA | グループ | 無料期限内 |
| 減8 | OTA | グループ | 有料期限後 |

> **注記**: グループツアーにおいてもD（催行回に別予約が残るか）は人数減員には影響しない。催行回の現在人数が減算されるだけで、無効化判定はしない（催行回が0件になるのは全件キャンセル時のみ）。

### 4-2. 業務フロー

```
1. 減員依頼を受ける（ゲスト / OTA経由）
2. 減員後の参加人数（または減員する人数）を入力
3. [価格計算] 減員後人数のTiered Pricingを確認
   - 減員後合計金額 = 減員後人数 × 減員後Tiered単価
   - キャンセル対象金額 = 元の販売金額 − 減員後合計金額
   ※ 減員により価格帯が上がると減員後合計金額が増え、キャンセル対象金額が小さくなる・マイナスになる場合は運営判断
4. キャンセル料判定日時（現在日時）を確認・記録
5. 予約時点のキャンセルポリシー（商品条件スナップショット）を参照
6. [G: 無料期限内] キャンセル料率 0%・全額（キャンセル対象金額）返金として確認
7. [G: 有料期限後] 適用キャンセル料率を確認
   - キャンセル料 = キャンセル対象金額 × キャンセル料率
   - 返金額 = キャンセル対象金額 − キャンセル料
8. 減員を承認・実行
```

### 4-3. システム処理フロー

**共通処理（全パターン）**
```
- 予約の参加人数を更新
- 販売金額を更新（減員後人数 × Tiered Price後の単価）
- 減員人数分のリソースを解放
- 催行回の現在人数を減算（無効化はしない）
- キャンセル料・返金額・適用ポリシーIDをレコードに記録
- 再手配要否フラグ = ON、変更理由区分 = 「減員」
- 変更履歴を保存（Tiered Price算出根拠・キャンセル対象金額・キャンセル料率・返金額を含む）
```

**処理後自動更新（共通）**
```
- 販売金額減分・チャネル手数料・ゲスト立替経費（減員人数分を減算）を自動再計算
```

**[B: 直販 × G: 無料期限内]**
```
- 返金レコードを作成（返金額 = キャンセル対象金額、キャンセル料 = 0）
- 返金ステータス = 「未処理」
- 決済手数料を自動再計算（返金方法次第で手数料変動の可能性を記録）
```

**[B: 直販 × G: 有料期限後]**
```
- 返金レコードを作成（返金額 = キャンセル対象金額 − キャンセル料）
- 返金ステータス = 「未処理」
- 決済手数料を自動再計算
```

**[B: OTA × G: 無料期限内]**
```
- 返金はOTAが処理。返金ステータス = 「OTA返金済み（Deep対応不要）」として記録
- 決済手数料の再計算なし
```

**[B: OTA × G: 有料期限後]**
```
- キャンセル料・返金額はDeep側で記録（OTA側ポリシーと差異があればメモ）
- 返金はOTAが処理。返金ステータス = 「OTA返金済み（Deep対応不要）」として記録
```

## 5. 全件キャンセル

全件キャンセルは最も条件が多い。H（予約ステータス）で大きく2分岐する。

---

### 5-1. H: 確定待ちのキャンセル

キャンセル料なし・返金不要。チャネル・期限・発生元に関係なく一律処理。

**条件とパターン**

| # | ツアー種別 | 催行回の状況 |
|---|---|---|
| キャ確1 | プライベート | 催行回が自動作成済み（確定紐付け）→ 無効化が必要 |
| キャ確2 | グループ | 仮紐付けあり → 解除が必要 |
| キャ確3 | グループ | 未紐付け → 催行回操作なし |

**業務フロー（確定待ち共通）**
```
1. 対象予約を開く
2. 発生元区分（ゲスト都合 / 運営都合 / 第三者都合）を選択
3. キャンセル理由を入力
4. キャンセル料率 0%・返金不要（販売未確定のため）として記録
5. キャンセルを確定
```

**システム処理フロー**

**[C: プライベート（キャ確1）]**
```
- 予約ステータスを「キャンセル済み」に更新
- 仮確保リソースを解放
- 催行回（確定紐付け）を「Cancelled（中止）」に更新
- ガイド手配ステータスを「キャンセル」・通知要否フラグ = ON
- 変更履歴を保存
```

**[C: グループ × 仮紐付けあり（キャ確2）]**
```
- 予約ステータスを「キャンセル済み」に更新
- 仮確保リソースを解放
- 旧催行回から仮紐付けを解除 → 旧催行回の現在人数を更新
  ├─ 更新後0件 → 催行回を自動無効化・ガイド手配を「キャンセル」・通知要否フラグON
  └─ 更新後1件以上 → 催行回存続・ガイド手配は維持・再手配要否フラグON
- 変更履歴を保存
```

**[C: グループ × 未紐付け（キャ確3）]**
```
- 予約ステータスを「キャンセル済み」に更新
- 仮確保リソースがあれば解放（未紐付け段階では通常なし）
- 催行回操作なし
- ガイド手配が始まっていれば「キャンセル」に更新
- 変更履歴を保存
```

---

### 5-2. H: 確定予約 × F: 運営都合キャンセル

キャンセル料なし・全額返金。期限に関係なく一律。チャネルは返金処理に影響。

**条件とパターン**

| # | チャネル | ツアー種別 | 旧催行回に別予約 |
|---|---|---|---|
| キャ運1 | 直販 | プライベート | （常に0件） |
| キャ運2 | OTA | プライベート | （常に0件） |
| キャ運3 | 直販 | グループ | 残る（1件以上） |
| キャ運4 | OTA | グループ | 残る（1件以上） |
| キャ運5 | 直販 | グループ | 0件になる |
| キャ運6 | OTA | グループ | 0件になる |

**業務フロー（運営都合共通）**
```
1. 対象予約を開く
2. 発生元区分「運営都合」を選択
3. キャンセル理由を入力（悪天候 / 施設都合 / ガイド確保不可 / 安全上の理由など）
4. キャンセル料率 0%・全額返金対象として確認（判定日時にかかわらず）
5. [STEP 3] 反映先（リソース・催行回・ガイド手配）の自動判定結果を確認
6. キャンセルを実行
7. [STEP 5] 全財務項目の一括確認・確定
```

**システム処理フロー（実行時）**

```
- 予約ステータスを「キャンセル済み」に更新
- リソース消費を全量解放
```

**[C: プライベート（キャ運1・2）]**
```
- 催行回を自動的に「Cancelled（中止）」に更新
- ガイド手配ステータスを「キャンセル」・通知要否フラグ = ON
```

**[C: グループ × D: 別予約残る（キャ運3・4）]**
```
- 旧催行回から予約を解除 → 現在人数を更新（催行回存続）
- ガイド手配は維持・再手配要否フラグ = ON・変更理由区分「運営都合キャンセル」
```

**[C: グループ × D: 0件になる（キャ運5・6）]**
```
- 旧催行回から予約を解除 → 有効予約0件 → 催行回を自動的に「Cancelled（中止）」に更新
- ガイド手配ステータスを「キャンセル」・通知要否フラグ = ON
```

## 7. 条件組み合わせ上の注意点

1. **プライベートツアーは常にD=0件**  
   プライベートツアーは1催行回=1予約の原則のため、日時変更・キャンセル時は旧催行回が必ず0件になり無効化される。Dによる分岐はグループツアーのみ。

2. **OTA経由予約はF=OTA経由とB=OTAが連動**  
   OTA経由で来たキャンセル（F=第三者都合）は、チャネルも必然的にB=OTA。ゲスト都合・運営都合のキャンセルがOTA経由チャネルの予約に対して発生することはある（例：運営都合で催行回全体をキャンセルする場合）。

3. **日時変更後のキャンセル料判定は変更後のツアー日を基準にする**  
   日時変更を経てからキャンセルした場合、キャンセル料の期限計算は変更後のツアー日（新日時）を使う。変更前のツアー日は使わない。判定で更新するのは判定日付（新日時）のみであり、適用するキャンセルポリシーは予約時点の商品条件スナップショットに固定したまま据え置く。日時変更によってポリシーのスナップショットを引き直すことはしない（TourOptionバージョン固定）。

4. **確定待ちのキャンセルは発生元・期限・チャネル問わずキャンセル料なし**  
   確定待ち状態は販売未確定のため、どの発生元・どのタイミングでもキャンセル料は発生しない。

5. **グループツアーのキャンセル時、催行回が0件になるかどうかは実行時に決まる**  
   事前に確認可能だが、他の予約の状況次第で変わるため、システムは実行時に有効予約件数を確認して自動判定する。

6. **同一旧催行回内は同一TourOptionバージョンのため新催行回へ集約可能**  
   催行回レコードはTourOption ID（TourOptionバージョン）を必須属性で保持し、紐付く全予約は同一TourOption ID（TourOptionバージョン混在禁止）。したがって旧催行回内の予約は全て同一TourOptionバージョンであり、日時変更・移動時に束ね鍵（TourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語の完全一致）が一致する新催行回があれば、TourOptionバージョン整合を保ったまま同一の新催行回へ集約できる。束ね鍵の正はTourOption IDであり、提供内容ハッシュは不採用。商品条件スナップショットID（予約時点スナップショット）は金額・ポリシー再現専用で束ね鍵には使わない。

## 8. 設計上の追加考慮事項（v2で追記）

### 8-1. 日時変更はキャンセルポリシー期限後には不可

日時変更の受付可否はキャンセルポリシーの無料キャンセル期限に連動する。

**適用範囲：** 期限ゲートはゲスト都合の日時変更に適用する。運営都合（天候・ガイド都合等）の日時変更は対象外。

**業務フロー上の扱い：**
- 無料キャンセル期限内 → 日時変更可能（通常フロー）
- 有料キャンセル期限後 → 日時変更は受け付けない。ゲストには「キャンセル料が発生するキャンセル扱い」として案内する。例外的に運営判断で承認する場合は例外承認の記録が必要

**背景：** 期限後の日時変更を自由に認めると、キャンセル料を回避する抜け道になる。変更によって旧日時のキャンセル料が免除される。

---

### 8-2. 追加請求（日時変更・人数増員の差額）が未払いの場合

追加請求を確定後、一定期間を過ぎてもゲストが支払わない場合の対応フロー：

| 選択肢 | 内容 | 条件 |
|---|---|---|
| a. 変更を取り消す | 変更前の状態に戻す（旧催行回を再有効化・新催行回を無効化・リソースを元に戻す）。旧催行回の再有効化時は、戻す予約のTourOption ID（固定TourOptionバージョン）と旧催行回のTourOption ID（TourOptionバージョン）が一致するかTourOptionバージョン整合を再検証する（TourOptionバージョン混在禁止のため）。実質キャンセル扱いになる場合はキャンセルポリシーを適用する | ゲストが変更自体に納得していない場合 |
| b. 未収のまま変更を維持 | 変更は成立させ、差額を売掛として管理。別途督促・回収を進める | ゲストとの関係を維持したい場合・督促中の場合 |
| c. 差額を免除（例外対応） | 対応方針を「変更なし」に変更し差額ゼロとして処理する | 例外承認が得られた場合。記録が必要 |

選択した対応内容と理由をシステムに記録し、変更・キャンセル履歴を更新する。

---

### 8-3. 旧催行回無効化時の元ガイド優先再アサイン確認フロー

旧催行回が無効化される日時変更（プライベートツアー全件・グループツアー×0件）の際、元アサインガイドを新催行回に優先的に再アサインすることを目指す。

**フロー：**
1. 旧催行回に紐付いていたガイド手配レコードを参照する
2. システムが新催行回のガイド手配画面に「旧催行回アサイン済みガイド：〇〇」を表示する
3. 担当者がそのガイドに新日時の空き状況を直接確認する
4. 空きあり → 同じガイドを優先的に新催行回へアサイン（ガイドの合意を得て確定）
5. 空きなし → 通常の新規ガイド選定フローへ。手配ステータス「未手配（要選定）」として開始

**グループ×別予約残るの場合の注意：** 旧催行回は存続するため元ガイドは旧催行回に残る。当該予約が移る新催行回は新規ガイド選定から開始する（同じガイドが両催行回を担当できる可能性は日程次第）。

---

### 8-4. OTA経由予約の人数増員 — 当日増員が判明した場合の例外

OTA経由予約の人数増員について、通常の業務フローは以下の通り：

- **キャンセル期限前の増員**：ゲストがOTA側で自ら人数を変更し、OTAが最新価格で請求する。Deep側の処理なし（「OTAが追加請求機能に対応していない」は例外ではない。期限前ならゲストがOTA上で自由に変更・再請求できるため）

**例外：当日現地で増員が判明した場合のみ、直販と同じ追加請求フローが発生する**

| 状況 | 理由 | 対応 |
|---|---|---|
| 当日現地での増員 | キャンセル期限後またはツアー当日のため、OTA側での変更手続きができない | ゲストに直接追加請求を行い、Deep側で請求レコードを作成・決済を処理する（直販と同フロー） |

---

### 8-5. 人数減員「有料期限後」でも返金が発生するケースがある

「有料キャンセル期限後」は「返金ゼロ」を意味しない。キャンセル料率がポリシー次第（30%・50%・70%・100%など）のため：

| キャンセル料率 | キャンセル料 | 返金額 | 返金ステータス |
|---|---|---|---|
| 0%（無料期限内） | 0円 | キャンセル対象金額の全額 | 未処理 |
| 50%（有料期限後） | キャンセル対象金額 × 50% | キャンセル対象金額 × 50% | 未処理 |
| 100%（返金不可商品・最終期限後など） | キャンセル対象金額 × 100% | 0円 | 不要 |

返金ステータスを「不要」にするのは料率が100%の場合のみ。それ以外は返金レコードを作成する。

---

### 8-6. 運営都合キャンセル × OTA経由予約のペナルティ

運営都合でOTA経由の予約をキャンセルした場合、OTAからペナルティ（違約金）が発生する可能性がある。

**フロー：**
1. キャンセル処理後、対象OTAにペナルティの有無・金額を確認する
2. 金額が判明したら、運営費精算（ガイド手配設計資料 §10-4）の独立科目「OTAペナルティ（運営都合違約金）」として記録する（チャネル手数料とは別の追加コスト。原価として管理し粗利から差し引く。予約の支払いステータスは「Penalty Applied」とする）
3. 金額が未確定の場合は「要確認」状態で保存し、判明後に更新する

**原価計上の一本化：** OTAペナルティの原価計上は運営費精算側（§10-4）に一本化する。変更・キャンセルレコード側には原価を重複計上しない（記録するのは「Penalty Applied」という支払いステータスの表現に留める）。これにより同一ペナルティが運営費精算と変更・キャンセルレコードの両方で二重計上されることを防ぐ。

**管理項目への追加：** チャネル設定または個別レコードに「OTA運営都合キャンセルペナルティポリシー」を記録しておくことが望ましい。ペナルティの有無・算出基準はOTA・チャネルの契約ごとに異なる。

**既存データ移行時の扱い：** 現行スプレッドシートではOTAペナルティを「チャネル手数料の調整」として記録している。新システムは独立した「OTAペナルティ」項目とするが、**ネット受取額・粗利はどちらの記録方法でも同値になるため、過去データの合計は保たれ移行は成立する**。移行ルールは次のとおり:
- 稼働後の新規予約 → 運営費精算（§10-4）の独立科目「OTAペナルティ」で記録。
- 既存行でペナルティ額が分離できる（別記・メモ等がある）→ 独立項目へ振り分けて移行。
- 既存行でペナルティが手数料に溶け込み分離できない → 手数料に含めたまま移行し、「手数料ペナルティ込み（移行）」フラグを付与する。
- 注意: 過去のチャネル手数料率を分析する際は、上記フラグの付いた行を除外する（ペナルティ込みのため率が高く見える）。

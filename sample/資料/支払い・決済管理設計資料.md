# 支払い・決済管理設計資料

## 1. この資料の目的

この資料は、DeepExperienceの新システムにおける「支払い・決済管理」の基本方針、データ構造、処理フロー、管理画面の設計方針と範囲を整理するための資料です。

支払い・決済管理の目的は以下です。

- 予約ごとの入金・返金・追加決済の状態を正確に記録・管理できる
- OTAからの入金をOTAレポートと照合し、入金漏れ・差異を検知できる
- キャンセル料・追加請求などの発生時に、決済処理の状況を追跡できる
- 売上・原価管理設計（予約収支レコード）と連携し、利益計算の入力を提供できる

本資料で扱う「支払い」とは、ゲストからDeepへの入金・Deep からゲストへの返金を指します。OTAからDeepへの入金管理（OTA照合）も本資料で扱います。

売上・利益の計算（グロス売上・チャネル手数料・ネット受取額・粗利など）は「売上・原価管理設計資料」で別途扱います。

---

## 2. 設計の基本方針

### 2-1. 初期MVPで実現したいこと

- 自社サイト予約（Stripe経由クレカ決済）の入金を予約と紐付けて管理できる
- OTA経由予約の入金をOTAレポートと照合し、照合結果を記録できる
- キャンセル時の返金処理状況（未処理 / 完了）を管理できる
- 追加請求・追加返金の発生を記録できる
- 各予約の支払い状況を一覧で確認できる

### 2-2. 初期MVPでやりすぎないこと

- 決済処理そのものの自動化（Stripe APIの自動実行など）
- OTA入金の自動照合（手動照合の記録に留める）
- 現金決済の本格的な管理フロー（例外処理として最小限記録）
- B2B（旅行会社・法人）向けの請求書発行・管理（MVP後に整備）
- 複数通貨の自動換算・管理

## 3. 決済の種類と対応フロー

### 3-1. 自社サイト予約（Stripe クレカ決済）

予約時にゲストがクレカで即時全額決済する。決済サービスはStripe想定（確定次第更新）。

**入金フロー**

```
ゲストが予約フォームで決済
  ↓
Stripe上で決済処理（PaymentIntent）
  ↓
Deep側システムに決済完了のWebhookが届く
  ↓
支払いレコードを作成・紐付け（→ §5）
  ↓
予約の支払いステータスを「支払い済み」に更新
```

**返金フロー（キャンセル時）**

```
運営がキャンセル処理を実行
  ↓
キャンセル料・返金額を確認（変更・キャンセル設計資料 §7 参照）
  ↓
運営がStripe管理画面またはシステム上から返金操作を実行
  ↓
返金レコードを作成（→ §6）
  ↓
予約の返金ステータスを「完了」に更新
```

返金額はStripeを通じて元のカードに返金される。

**追加請求・差額返金（増員・減員時）**

増員・減員時の追加請求・差額返金は、Stripeの保存済み決済方法を使った追加チャージまたは追加返金として処理することを想定する。

初期MVPでは、追加請求・追加返金の実行そのものはシステム外（Stripe管理画面での操作）とし、システムでは発生した追加支払いレコード・追加返金レコードの記録管理のみを対象とする。

---

### 3-2. OTA経由予約

OTA（Viator・GetYourGuide・Klookなど）はゲストから直接集金し、手数料を差し引いたネット額をDeepに支払う。支払いタイミングはOTAごとに異なる（月次・隔週など）。

OTA経由予約の支払いは、DeepがOTAレポートと銀行口座の入金を照合して確認する。

**OTA入金フロー**

```
OTAのレポート（月次など）をOTA管理画面またはメールで受領
  ↓
銀行口座への入金額とOTAレポートの合計額を照合
  ↓
OTA入金レコードを作成（→ §7）
  ↓
OTAレポートの各行（予約単位）を社内予約と紐付け
  ↓
照合結果（一致 / 差異）を記録
```

OTA経由のキャンセル・返金は、原則としてOTA側で行われる。Deep側では返金ステータスに「OTA返金済み（Deep対応不要）」を記録するのみ。

---

### 3-3. 現金決済（例外対応）

現金決済は通常の販売フローには含まない。金額が大きい特殊なケースでのみ例外対応として発生する可能性があるため、記録できる構造だけ持つ。

支払い方法として「現金」を選択できるようにし、金額・受領日・受領担当者を記録する。返金は別途銀行振込などで個別対応。

---

### 3-4. B2B（旅行会社・法人）

初期MVPでは対象外。現状は個別対応のため、MVP後に旅行会社・法人向けの支払いフローを別途設計する。

MVPでは支払い方法として「法人後払い（要確認）」を選択できるようにし、個別メモで管理する。

---

### 3-5. 追加請求フロー（決済リンク発行〜入金確認）

追加請求が発生するのは主に以下のケース：

- 日時変更による価格差額（対応方針「追加請求」を選択した場合）
- 人数増員による追加費用（直販、またはOTA経由で当日増員が判明した場合）

#### 業務フロー（初期MVP：手動操作）

```
変更・キャンセル処理で追加請求額が確定
 ↓
① 【決済リンク発行】Stripe管理画面でPayment Linkを発行
     金額：確定した追加請求額
     有効期限：発行日から○日（運用基準に従い設定）
 ↓
② 【ゲスト連絡】決済リンクをゲストへ送付（メール / LINE / WhatsApp など）
     内容：追加請求の理由・金額・支払い期限日を明記
 ↓
③ 【Deep側記録】追加支払いレコードにリンクURL・送付日時を記録
     追加請求ステータスを「請求済み（未払い）」に更新
     予約の支払いステータスを「Partially Paid」に更新
 ↓
④ 【ゲスト決済】ゲストが決済リンクから支払い
 ↓
⑤ 【入金確認】Stripe Webhookで決済完了通知を受信
     または 担当者がStripe管理画面で入金を確認
 ↓
⑥ 【記録更新】追加支払いレコードのステータスを「支払い済み」に更新
     予約の支払いステータスを更新（Partially Paid → 支払い済み）
```

#### 未払い時のリマインダーフロー

```
追加請求の送付後
 ↓
担当者が支払い状況を確認（一定期間後）
 ↓
未払いの場合：再連絡・リマインダーを送付
 ↓
さらに未払いが続く場合：変更・キャンセル設計 §8-2 の
「追加請求未払い時の対応フロー」に従い選択する
  a. 変更を取り消す
  b. 未収のまま変更を維持（売掛として管理）
  c. 差額を免除（例外対応）
→ 選択した対応方針を記録し追加請求ステータスを更新する
```

#### 追加請求ステータス

| ステータス | 意味 |
|---|---|
| 未送付 | 追加請求額は確定したが、まだゲストへ連絡していない |
| 請求済み（未払い） | 決済リンクを送付済みだが、まだ入金されていない |
| 支払い済み | ゲストの入金が確認できた |
| 期限切れ | 決済リンクの有効期限が切れた（再発行が必要） |
| 取消 | 変更取消・差額免除などにより追加請求が不要になった |

> **将来対応（MVP後）：** Stripe APIを使って決済リンクをシステムから自動生成し、メール・LINE等への自動送付と未払いリマインダーの自動送信まで対応することを想定する。

## 4. 支払いステータス

### 4-1. 予約レベルの支払いステータス

| ステータス | 意味 |
|---|---|
| 未払い | まだ入金がない状態（Unpaid）|
| Partially Paid | 総請求額の一部のみ入金済み。追加支払いの未回収・代理店分割入金などを含む |
| 支払い済み | 総請求額が全額入金済みの状態（Paid in Full）|
| 支払い不要 | キャンセル等で請求が発生しない状態（Not Charged）|
| 部分返金済み | 一部返金が完了した状態（Partially Refunded）|
| 全額返金済み | 全額が返金済みの状態（Refunded）|
| Chargeback / Disputed | クレジットカードのチャージバック申請または支払い争議が発生した状態 |
| Penalty Applied | 運営都合キャンセルによりOTAからペナルティを受けた状態を表す支払いステータス。ペナルティの原価計上は運営費精算側（ガイド手配設計資料 §10-4「OTAペナルティ（運営都合違約金）」）に一本化し、本ステータスは支払い側・変更／キャンセルレコードに原価を重複計上しない（支払いステータスの表現に留める） |
| 要確認 | 入金状況が不明・照合待ちの状態 |

### 4-2. 返金ステータス

変更・キャンセル設計資料の返金ステータス定義と共通。

| ステータス | 説明 |
|---|---|
| 未処理 | 返金が必要だが、まだ完了していない。進捗はメモ欄で管理 |
| 完了 | 返金が完了した |
| 不要 | 返金が発生しない（キャンセル料率100%など） |
| OTA返金済み（Deep対応不要） | OTA側が返金処理済み |
| 要確認 | OTA側の返金状況が不明・確認待ち |
| 特別対応中 | Deep側が独自の追加対応を進めている |

## 8. 決済関連の画面・機能

### 8-1. 予約詳細内の支払いサマリー

目的：予約詳細画面で、当該予約の支払い状況を把握できる。

表示内容：

- 販売金額（予約時点の基準価格）
- 支払い済み金額（Stripe決済額 または OTA経由入金済み額）
- 支払いステータス
- 返金額・返金ステータス（キャンセル時）
- 追加支払い額（増員時など）
- 支払い履歴一覧（支払いレコード・返金レコードの時系列）

### 8-2. OTA入金照合画面

目的：OTAからの入金を登録し、OTAレポートと照合できる。

必要機能：

- OTA入金レコードの新規登録（入金日・対象OTA・金額・対象期間）
- OTAレポートの各予約行を社内予約に紐付ける照合操作
- 照合差額の確認（銀行入金額 vs OTAレポート合計）
- 照合ステータスの更新（差異があればメモを記録）
- 照合の完了操作：全行照合後に「照合完了」とする。差異がある場合は差異理由を記録のうえ「差異を承認して完了」とし、完了者・完了日時を記録する（差異理由が未記録のうちは完了できない）
- 未照合予約の一覧表示

### 8-3. 返金管理画面（予約詳細内）

目的：返金処理の実行記録と進捗管理。

必要機能：

- 返金レコードの新規登録（返金額・返金方法・実行日）
- 返金ステータスの更新（未処理 → 完了）。進捗はメモ欄で管理
- Stripe返金参照IDの記録

### 8-4. 追加請求管理（予約詳細内）

目的：追加請求の発行・送付・入金確認を一元管理する。

必要機能：

- 追加支払いレコードの新規登録（追加請求額・発生元の変更処理との紐付け）
- 決済リンクURL・有効期限・送付日時・送付手段の記録
- 追加請求ステータスの更新（未送付 → 請求済み → 支払い済み / 取消など）
- 期限切れリンクの検知（有効期限を過ぎても未払いの場合に担当者が気づけるようにする）
- 未払い一覧：支払い期限が近い・過ぎた追加請求を一覧で確認できる画面（初期はフィルター機能で対応）

## 9. 売上・原価管理設計との連携

本資料で管理する支払いレコードは、「売上・原価管理設計資料」の予約収支レコードと以下のように連携します。

| 売上・原価管理の項目 | 参照元 |
|---|---|
| グロス売上 | OTA経由・自社とも：販売金額（予約レコード） |
| チャネル手数料 | OTA経由：OTA照合レコードのOTAレポート上手数料 / 自社：0%（チャネル手数料なし） |
| 決済手数料 | Stripe：決済方法マスターの手数料率で計算 |
| ネット受取額 | グロス売上 − チャネル手数料 − 決済手数料 |

| 機能 | 優先度 |
|---|---|
| 予約詳細での支払いサマリー表示 | 必須 |
| 支払いレコードの登録・確認 | 必須 |
| 返金レコードの登録・ステータス管理 | 必須 |

| OTA照合（手動）の記録 | 必須 |

| 現金支払いの記録 | 最小限 |

## 11. 初期MVPで対象外にするもの

| 項目 | 理由 |
|---|---|
| Stripe APIを使った追加請求・返金の自動実行 | MVP後。初期はStripe管理画面での手動操作＋記録に留める |
| OTA入金の自動照合 | OTA APIとの連携が必要なため後続フェーズ |
| B2B請求書発行・管理 | 現状個別対応中のためMVP後に設計 |
| 複数通貨の換算管理 | 初期はJPYのみ |
| 入金確認の自動通知（ゲスト向け） | 通知設計の別資料で扱う |

## 12. 初期MVPの完了条件

以下ができる状態を完了条件とします。

- 予約詳細で支払い状況（支払い済み / 返金ステータス）を確認できること
- 自社クレカ決済の支払いレコードを登録・確認できること
- OTA経由予約の入金レコードを登録し、照合結果を記録できること
- キャンセル時の返金レコードを作成し、ステータスを管理できること
- 追加支払い・差額返金のレコードを登録できること

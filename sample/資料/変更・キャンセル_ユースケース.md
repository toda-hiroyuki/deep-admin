# 変更・キャンセル ユースケース一覧

本資料は「変更・キャンセル設計資料」の補足資料として、運営担当者が行う変更・キャンセル処理の具体的な操作フローを整理するものです。

---

## ユースケース概要

| UC | 種別 | 名称 | 発生元 | キャンセル料 |
|---|---|---|---|---|
| UC-01 | 日時変更 | ゲスト都合での日時変更 | ゲスト / OTA | なし |
| UC-02 | 日時変更 | 運営都合での日時変更 | 運営 | なし |
| UC-03 | 人数変更 | 参加人数の増員 | ゲスト / OTA | なし |
| UC-04 | 人数変更 | 参加人数の減員（部分キャンセル） | ゲスト / OTA | 期限による |
| UC-05 | キャンセル | 確定待ち予約のキャンセル | 任意 | **なし（確定前のため）** |
| UC-06 | キャンセル | ゲスト都合キャンセル（無料期限内） | ゲスト / OTA | なし |
| UC-07 | キャンセル | ゲスト都合キャンセル（有料期限後） | ゲスト / OTA | ポリシー適用 |
| UC-08 | キャンセル | 運営都合キャンセル | 運営 | **なし（全額返金）** |
| UC-09 | キャンセル | OTA経由キャンセルの受付処理 | OTA | OTA側で処理済み |

---

## 共通前提

- すべての処理は**運営担当者が手動で実行する**（初期MVPではゲスト自身による操作は対象外）
- キャンセル料の計算は手動で行い、算出根拠（判定日時・適用ポリシー）をシステムに記録する
- 返金処理そのものはシステム外で行い、システムでは返金情報の記録・ステータス管理のみ行う
- **日時変更後のキャンセル料判定基準は、変更後のツアー日とする**（変更前のツアー日は使わない）
- ガイドへの連絡通知は手動で行う（システムは「通知要否フラグ」を立てるのみ）

---

## 価格計算について（変更・キャンセル時）

### 段階価格（Tiered Pricing）

本システムでは、参加合計人数に応じて1名あたりの単価が変わる**段階価格（Tiered Pricing）**を採用する。

例：

| 参加合計人数 | 1名あたり単価 |
|---|---|
| 1〜2名 | 10,000円 |
| 3〜5名 | 8,000円 |
| 6〜8名 | 7,000円 |

人数が変わると単価が変わるため、**単純な「変更人数 × 元の単価」では正確な金額が算出できない**。人数変更時は必ず変更後の合計人数で価格帯を再確認する。

### 日時変更と価格

TourOptionの価格はMVPでは日付を持たない固定定義だが、予約後に**価格改定・割引・キャンペーン適用**が行われた場合、変更処理時点の価格と予約時点の価格（商品条件スナップショット）が異なる可能性がある。

日時変更を処理する際は、変更後に適用される現時点の価格を必ず予約時点の価格と照合し、差額の有無を確認・記録する。

### 人数変更時の金額算出フロー

**増員の場合（UC-03）：**

```
変更後合計金額 = 変更後人数 × 変更後単価（Tiered）
追加請求額    = 変更後合計金額 − 元の販売金額
```

**減員・部分キャンセルの場合（UC-04）：**

```
変更後合計金額    = 減員後人数 × 減員後単価（Tiered）
キャンセル対象金額 = 元の販売金額 − 変更後合計金額
キャンセル料      = キャンセル対象金額 × キャンセル料率
返金額           = キャンセル対象金額 − キャンセル料
```

具体例（元：6名 → 4名に減員、キャンセル料率 50%）：

| | 元の予約 | 減員後 |
|---|---|---|
| 参加人数 | 6名 | 4名 |
| 適用単価（Tiered） | 7,000円/名 | 8,000円/名 |
| 合計金額 | 42,000円 | 32,000円 |
| キャンセル対象金額 | — | **10,000円**（差額） |
| キャンセル料（50%） | — | 5,000円 |
| 返金額 | — | 5,000円 |

## UC-01: ゲスト都合での日時変更

**目的**: ゲストからの日時変更依頼を受け、新しいツアー日時で予約を更新する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定予約」。ゲストまたはOTA経由で日時変更依頼を受けている。**無料キャンセル期限内であること**（期限経過後＝有料キャンセル期間に入った予約の日時変更は受け付けず、キャンセル＋新規予約として案内する）。 |

**メインフロー**

1. 対象予約を開く
2. TourOption の「日程変更可否」と無料キャンセル期限内であることを確認する → 両方を満たす場合に続く
3. 変更後のツアー日・開始時間を入力する
4. **[価格確認]** 変更後に適用される現時点のTourOption価格を確認する
5. 予約時点の販売価格（商品条件スナップショット）と照合し、差額の有無を確認する。差額がある場合は対応方針（追加請求 / 差額返金 / 変更なし）を決定・記録する
6. 新日時でのリソース空きを確認する（上限チェック）
7. **[グループツアー]** 新日時で紐付け可能な催行回を確認する
8. 変更を確定し、予約のツアー日・開始時間を更新する（対応方針に応じて販売価格も更新する）
9. 旧日時のリソース消費を解放する
10. 新日時のリソースを確保する
11. **[プライベートツアー]** 旧催行回を無効化し、新日時で催行回を自動生成・即確定紐付けとする
12. **[グループツアー]** 旧催行回から予約を解除し旧催行回の現在人数を更新する。新催行回に仮紐付けする（または新規催行回を作成して割り当てる）
13. ガイド手配を更新する。日時が変わるため再手配要否フラグをONにし、変更理由区分「日時変更」を記録する。旧催行回が無効化された場合（プライベートツアー、またはグループツアーで旧催行回の残存有効予約件数が0件になった場合）は旧催行回のガイド手配ステータスを「キャンセル」に更新する。旧催行回が存続する場合は手配ステータスは変更しない（「確定」を維持）
14. 発生元区分・変更理由・価格差額対応方針・処理者・処理日時を記録し、変更・キャンセル履歴を保存する

**代替フロー**

- **6a. リソースに空きがない場合**: 変更不可として記録する。運営がゲストに連絡し、別日時を検討する
- **7a. [グループツアー] 新日時の適切な催行回がない場合**: 新規催行回を作成してから紐付ける
- **2a. TourOptionが「日程変更不可」の場合**: 運営が例外承認するか判断する。承認する場合は例外承認の旨を変更記録に残してメインフローに戻る
- **2b. 無料キャンセル期限を過ぎている（有料キャンセル期間に入っている）場合**: 日時変更は受け付けない。ゲストには「キャンセル料が発生するキャンセル扱い」とし、キャンセル（UC-07）＋新規予約として案内する。例外的に運営判断で承認する場合は例外承認の旨を変更記録に残してメインフローに戻る
- **5a. 差額があり「変更なし」を選択した場合**: 販売価格はそのまま維持し、差額対応方針を「変更なし」として記録する

**事後条件**

| 反映先 | 状態 |
|---|---|
| 予約 | ツアー日・開始時間が更新済み。販売価格が対応方針に応じて更新済み |
| リソース | 旧日時分が解放・新日時分が確保されている |
| 催行回 | 旧催行回から解除・新催行回に紐付け済み |
| ガイド手配 | 再手配要否フラグON・変更理由区分「日時変更」が記録済み。旧催行回が無効化された場合（プライベート、またはグループで残存有効予約件数0件）→ 旧催行回のガイド手配ステータスが「キャンセル」/ 旧催行回が存続する場合 → 手配ステータスは「確定」のまま |
| 変更履歴 | 変更前後の日時・価格差額対応方針・発生元・処理者・処理日時が記録済み |

## UC-02: 運営都合での日時変更

**目的**: 悪天候・施設都合などにより、運営側の判断でツアー日時を変更する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定予約」。悪天候・施設都合・安全上の理由などが発生している。 |

**メインフロー**

1. 対象予約を開く
2. 発生元区分「運営都合」を選択し、変更理由を入力する（悪天候・施設都合・安全上の理由など）
3. 代替日時を確認・決定する
4. 新日時でのリソース確保を確認する
5. 変更を確定し、予約のツアー日・開始時間を更新する
6. 旧日時のリソースを解放し、新日時のリソースを確保する
7. 催行回を更新する（UC-01 のステップ 9〜10 と同様）
8. ガイド手配を更新する。日時が変わるため再手配要否フラグをONにし、変更理由区分「日時変更」を記録する。旧催行回が無効化された場合（プライベートツアー、またはグループツアーで旧催行回の残存有効予約件数が0件になった場合）は旧催行回のガイド手配ステータスを「キャンセル」に更新する。旧催行回が存続する場合は手配ステータスは変更しない（「確定」を維持）
9. 変更・キャンセル履歴を保存する

**代替フロー**

- **3a. 代替日時が確保できない場合**: 日時変更ではなく運営都合キャンセル（UC-08）として処理する

**事後条件**

UC-01 の事後条件と同様。発生元区分が「運営都合」として記録されている点が異なる。

> **注意**: 運営都合による日時変更ではキャンセル料は発生しない。変更に応じないゲストへの対応は、運営都合キャンセル（UC-08）として扱う。

## UC-03: 参加人数の増員

**目的**: ゲストの依頼で参加人数が増え、Tiered Pricingで追加料金を算出し、リソース・催行回の管理数を更新する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定予約」。ゲストまたはOTA経由で増員依頼を受けている。 |

**メインフロー**

1. 対象予約を開く
2. 変更後の参加人数を入力する
3. **[価格計算]** 変更後の合計人数が該当するTiered Pricingの価格帯を確認する
4. 変更後の合計金額（= 変更後人数 × 変更後単価）を算出し、追加請求額（= 変更後合計金額 − 元の販売金額）を記録する
5. 追加人数分のリソースに空きがあるか確認する（上限チェック）
6. **[グループツアー]** 催行回の定員（最大人数）を超えないか確認する
7. 増員を確定し、予約の参加人数と販売金額を更新する
8. 追加人数分のリソースを確保する
9. 催行回の現在人数を更新する
10. 手配ステータスは変更しない（「確定」を維持）。再手配要否フラグをONにし、変更理由区分「増員」を記録する
11. 変更・キャンセル履歴を保存する（追加請求額を含む）

**代替フロー**

- **5a. リソースに空きがない場合**: 増員不可として記録する
- **6a. [グループツアー] 催行回の定員を超える場合**: 増員不可とする。または別催行回への分割を運営が判断する（分割は手動操作）。同一催行回に留める必要がある場合は、運営が**特例承認のうえ当該催行回の定員（ソフト上限）のみを拡張**して受け入れることができる（理由・承認者・拡張前後の定員を記録。リソース管理・催行回設計資料 §4-9）。ただし**リソース上限（ハード）は免除しない**ため、リソースに空きがない場合（5a）は特例拡張しても受け入れられない
- **3a. 増員により価格帯が下がる場合**（例：2名→6名で単価が安くなる）: 追加請求額は（変更後合計金額 − 元の販売金額）として正しく算出される。価格帯が下がっても人数増加分の総額は上がる点を確認する

**事後条件**

| 反映先 | 状態 |
|---|---|
| 予約 | 参加人数・販売金額が更新済み |
| リソース | 追加人数分が確保されている |
| 催行回 | 現在人数が更新済み |
| ガイド手配 | 手配ステータスは「確定」のまま。再手配要否フラグON・変更理由区分「増員」が記録済み（追加ガイドの要否確認待ち） |
| 変更履歴 | 変更前後の人数・Tiered Price算出根拠・追加請求額・処理者・処理日時が記録済み |

> **注意**: 増員によるキャンセル料は発生しない。算出した追加請求額は支払い管理側で請求処理する。

## UC-04: 参加人数の減員（部分キャンセル）

**目的**: 参加人数の一部がキャンセルになり、Tiered Pricingでキャンセル対象金額を算出したうえでキャンセル料を判定・記録し、人数を更新する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定予約」。ゲストまたはOTA経由で減員（部分キャンセル）依頼を受けている。 |

**メインフロー**

1. 対象予約を開く
2. 減員後の参加人数（または減員する人数）を入力する
3. **[価格計算]** 減員後の合計人数が該当するTiered Pricingの価格帯を確認する
4. 減員後の合計金額（= 減員後人数 × 減員後単価）を算出する
5. キャンセル対象金額（= 元の販売金額 − 減員後の合計金額）を算出する
6. キャンセル料判定日時（現在日時）を確認・記録する
7. 予約時点のキャンセルポリシー（商品条件スナップショット）を参照する
8. 現在日時とツアー日の差分を確認し、適用キャンセル料率を確認する
9. キャンセル料（= キャンセル対象金額 × キャンセル料率）と返金額（= キャンセル対象金額 − キャンセル料）を算出・入力する（手動算出）
10. 減員・部分キャンセルを確定し、予約の参加人数と販売金額を更新する
11. 減員分のリソース消費を解放する
12. 催行回の現在人数を更新する
13. キャンセル料・返金情報・Tiered Price算出根拠を含む変更・キャンセル履歴を保存する
14. 手配ステータスは変更しない（「確定」を維持）。再手配要否フラグをONにし、変更理由区分「減員」を記録する

**代替フロー**

- **8a. 無料キャンセル期限内の場合**: キャンセル料率 0%・キャンセル対象金額の全額返金として記録する
- **残り人数が最小人数条件を下回る場合**: 自動強制はしない。運営が全件キャンセル（UC-06〜07）への切り替えを判断する
- **3a. 減員により価格帯が上がる場合**（例：6名→4名で単価が高くなる）: 減員後合計金額が増えることがある。その場合、キャンセル対象金額は小さくなる（またはマイナスになる）ため、運営が別途判断する

**事後条件**

| 反映先 | 状態 |
|---|---|
| 予約 | 参加人数・販売金額が更新済み |
| リソース | 減員分が解放されている |
| 催行回 | 現在人数が更新済み |
| ガイド手配 | 手配ステータスは「確定」のまま。再手配要否フラグON・変更理由区分「減員」が記録済み |
| 変更履歴 | Tiered Price算出根拠・キャンセル対象金額・キャンセル料率・キャンセル料・返金額・適用ポリシーIDが記録済み |

## UC-05: 確定待ち予約のキャンセル

**目的**: リクエスト予約で「確定待ち」の予約がキャンセルになった場合に、キャンセル料なしで処理する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定待ち」（リクエスト予約で未確定）。ゲストまたは運営からキャンセルの依頼・判断がある。 |

**メインフロー**

1. 対象予約を開く
2. 発生元区分を選択する（ゲスト都合 / 運営都合 / 第三者都合）
3. キャンセル理由を入力する
4. キャンセル料率 0%・返金不要（販売未確定のため）として記録する
5. 予約ステータスを「キャンセル済み」に更新する
6. リソースが仮確保されていれば解放する（仮確保がない場合は操作不要）
7. **[グループツアー]** 催行回に仮紐付けされていれば解除する。**[プライベートツアー]** 予約受付時に催行回が自動作成され確定紐付けになっているため、当該催行回を Cancelled（中止）にする
8. ガイド手配が始まっていれば、以下のとおり更新する。**[プライベートツアー]** 催行回を無効化した場合は手配ステータスを「キャンセル」に更新し、通知要否フラグをONにする。**[グループツアー]** 仮紐付け解除後も催行回に他の有効予約が残る場合は手配を維持し、再手配要否フラグをONにする。残存有効予約が0件になった場合（催行回はシステムが自動的に無効化する）は手配ステータスを「キャンセル」に更新し、通知要否フラグをONにする
9. 変更・キャンセル履歴を保存する

**事後条件**

| 反映先 | 状態 |
|---|---|
| 予約 | ステータスが「キャンセル済み」 |
| リソース | 仮確保分があれば解放済み |
| 催行回 | グループ: 仮紐付けがあれば解除済み / プライベート: 催行回が Cancelled（中止）済み |
| ガイド手配 | 手配開始済みの場合: プライベート・グループ残存0件（催行回 Cancelled（中止））→ ステータスが「キャンセル」・通知要否フラグON / グループで他の有効予約が残る → 手配維持・再手配要否フラグON |
| 変更履歴 | キャンセル料なし・発生元・理由が記録済み |

> **根拠**: 予約がまだ確定していないため、キャンセルポリシーは適用しない。

## UC-06: ゲスト都合キャンセル（無料キャンセル期限内）

**目的**: 無料キャンセル期限内にゲストが全件キャンセルを申請し、キャンセル料なしで処理する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定予約」。キャンセル処理日時 < 無料キャンセル期限（= ツアー日 − ポリシーの無料期間）。 |

**メインフロー**

1. 対象予約を開く
2. 発生元区分「ゲスト都合」を選択し、キャンセル理由を入力する
3. キャンセル料判定日時（現在日時）を記録する
4. 予約時点のキャンセルポリシー（商品条件スナップショット）を参照する
5. 無料キャンセル期限内であることを確認し、キャンセル料率 0%・全額返金対象として記録する
6. キャンセルを確定し、予約ステータスを「キャンセル済み」に更新する
7. リソース消費を全量解放する
8. 催行回の現在人数を更新する（残存有効予約が0件になればシステムが自動的に無効化する）
9. 催行回の残存有効予約件数に応じてガイド手配を更新する。0件（催行回 Cancelled（中止））の場合は手配ステータスを「キャンセル」に更新し、通知要否フラグを立てる。1件以上（催行回存続）の場合は手配を維持し、再手配要否フラグをONにする
10. 変更・キャンセル履歴を保存する

**事後条件**

| 反映先 | 状態 |
|---|---|
| 予約 | ステータスが「キャンセル済み」 |
| リソース | 全量解放済み |
| 催行回 | 現在人数が更新済み（必要に応じて無効化） |
| ガイド手配 | 残存予約0件（催行回 Cancelled（中止））→ ステータスが「キャンセル」・通知要否フラグON / 1件以上（催行回存続）→ 手配維持・再手配要否フラグON |
| 変更履歴 | キャンセル料率0%・返金額・適用ポリシーIDが記録済み |

> **注意**: 返金処理は別途実施する。返金ステータスは「未処理」として記録し、完了後に更新する。

## UC-07: ゲスト都合キャンセル（有料キャンセル期限後）

**目的**: 有料キャンセル期限後にゲストが全件キャンセルを申請し、キャンセル料を算出・記録したうえで処理する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定予約」。キャンセル処理日時 ≥ キャンセル料発生タイミング（ポリシーで定義）。 |

**メインフロー**

1. 対象予約を開く
2. 発生元区分「ゲスト都合」を選択し、キャンセル理由を入力する
3. キャンセル料判定日時（現在日時）を記録する
4. 予約時点のキャンセルポリシー（商品条件スナップショット）を参照する
5. 現在日時とツアー日の差分から、適用キャンセル料率を確認する
6. キャンセル料（= 販売金額 × キャンセル料率）を算出し入力する（手動算出）
7. 返金額（= 販売金額 − キャンセル料）を算出し入力する
8. キャンセルを確定し、予約ステータスを「キャンセル済み」に更新する
9. リソース消費を全量解放する
10. 催行回の現在人数を更新する（残存有効予約が0件になればシステムが自動的に無効化する）
11. 催行回の残存有効予約件数に応じてガイド手配を更新する。0件（催行回 Cancelled（中止））の場合は手配ステータスを「キャンセル」に更新し、通知要否フラグを立てる。1件以上（催行回存続）の場合は手配を維持し、再手配要否フラグをONにする
12. 変更・キャンセル履歴を保存する

**代替フロー**

- **5a. 返金不可フラグ付き商品の場合**: キャンセル料率 100%・返金額 0 として記録する
- **[日時変更後にキャンセルが発生した場合]**: 判定基準は**変更後のツアー日**とする（変更前のツアー日は使わない）

**事後条件**

UC-06 と同様。キャンセル料・返金額・適用ポリシーIDが記録されている点が異なる。

## UC-08: 運営都合キャンセル

**目的**: 悪天候・施設都合・ガイド確保不可などにより、運営側の判断でキャンセルし、全額返金対象として記録する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | 予約ステータスが「確定予約」。悪天候・施設都合・ガイド確保不可・安全上の理由などが発生している。（「確定待ち」の運営都合キャンセルは UC-05＝キャンセル料なし・返金不要に一本化する。全条件別§5-2の確定予約限定スコープに合わせる） |

**メインフロー**

1. 対象予約を開く
2. 発生元区分「運営都合」を選択する
3. キャンセル理由を入力する（悪天候 / 施設都合 / ガイド確保不可 / 安全上の理由など）
4. キャンセル料率 0%・全額返金対象として記録する（キャンセル処理日時にかかわらず）
5. キャンセルを確定し、予約ステータスを「キャンセル済み」に更新する
6. リソース消費を全量解放する
7. 催行回の現在人数を更新する
8. 催行回の残存有効予約件数に応じてガイド手配を更新する。0件（催行回 Cancelled（中止））の場合は手配ステータスを「キャンセル」に更新し、通知要否フラグを立てる（アサイン済みガイドへの連絡が必要な状態にする）。1件以上（催行回存続）の場合は手配を維持し、再手配要否フラグをONにする
9. 変更・キャンセル履歴を保存する

**事後条件**

UC-06 と同様。発生元区分が「運営都合」・キャンセル料率が 0% として記録されている。

> **注意**: 同一催行回の複数予約を一括キャンセルする場合は、予約ごとに本フローを繰り返す（初期MVPでは一括処理は対象外）。

## UC-09: OTA経由キャンセルの受付処理

**目的**: OTA側でキャンセルが処理された通知を受け取り、Deep側でも予約をキャンセル済みにし、返金状況を記録する

| 項目 | 内容 |
|---|---|
| アクター | 運営担当者 |
| 事前条件 | OTA（またはBokun）からキャンセル通知を受け取っている。Deep側で対象予約が「確定予約」状態。 |

**メインフロー**

1. OTA管理画面またはメール通知でキャンセルを確認する
2. Deep システムで対象予約を特定する（外部予約番号・TourOptionコードなどで検索する）
3. 発生元区分「第三者都合」を選択する
4. OTA側のキャンセル処理日時・ポリシー適用状況を確認し、メモに記録する
5. Deep側の返金ステータスを「OTA返金済み（Deep対応不要）」として記録する
6. Deep側のポリシーとOTA側のポリシーに差異があればメモに記録する
7. キャンセルを確定し、予約ステータスを「キャンセル済み」に更新する
8. リソース消費を全量解放する
9. 催行回の現在人数を更新する
10. 催行回の残存有効予約件数に応じてガイド手配を更新する。0件（催行回 Cancelled（中止））の場合は手配ステータスを「キャンセル」に更新し、通知要否フラグを立てる。1件以上（催行回存続）の場合は手配を維持し、再手配要否フラグをONにする
11. 変更・キャンセル履歴を保存する

**代替フロー**

- **5a. OTA側の返金処理が不明または要確認の場合**: 返金ステータスを「要確認」として記録し、OTA確認後に更新する
- **5b. Deep側が独自の追加対応を行う必要がある場合**: 返金ステータスを「特別対応中」として記録し、完了後に「完了」に更新する

**事後条件**

| 反映先 | 状態 |
|---|---|
| 予約 | ステータスが「キャンセル済み」 |
| リソース | 全量解放済み |
| 催行回 | 現在人数が更新済み |
| ガイド手配 | 残存予約0件（催行回 Cancelled（中止））→ ステータスが「キャンセル」・通知要否フラグON / 1件以上（催行回存続）→ 手配維持・再手配要否フラグON |
| 変更履歴 | 発生元「第三者都合」・返金受領先「OTA経由」・返金ステータスが記録済み |

> **注意**: 返金ステータスは後から更新可能にする。OTA確認後に最終状態（「OTA返金済み」「完了」など）に更新する。

## ユースケース間の関係とフロー判断

```
変更・キャンセル依頼を受ける
│
├─ 変更の種別は？
│   ├─ 日時変更
│   │   ├─ ゲスト都合 → UC-01
│   │   └─ 運営都合 → UC-02（代替日なければ UC-08 へ）
│   │
│   └─ 人数変更
│       ├─ 増員 → UC-03
│       └─ 減員（部分キャンセル） → UC-04
│
└─ キャンセルの場合
    ├─ 予約ステータスが「確定待ち」？ → UC-05（キャンセル料なし）
    │
    └─ 予約ステータスが「確定予約」
        ├─ 発生元が運営都合？ → UC-08（キャンセル料なし・全額返金）
        ├─ 発生元がOTA？ → UC-09（OTA返金済みとして記録）
        └─ 発生元がゲスト都合
            ├─ 無料キャンセル期限内？ → UC-06（キャンセル料なし）
            └─ 有料キャンセル期限後？ → UC-07（ポリシー適用）
```

## 返金ステータス一覧

OTA経由・通常返金を含む返金ステータスは以下の値で管理する。後からの更新を可能にする。

| 返金ステータス | 説明 | 主な用途 |
|---|---|---|
| 未処理 | 返金が必要だが、まだ処理していない | UC-06、UC-07 での処理直後 |
| 完了 | 返金が完了した | 返金確認後に更新 |
| 不要 | 返金が発生しない（キャンセル料率100%・返金不可商品など） | UC-07 の一部 |
| OTA返金済み（Deep対応不要） | OTA側が返金処理済みのためDeepは対応不要 | UC-09 のデフォルト |
| 要確認 | OTA側の返金状況が不明・確認待ち | UC-09 の代替フロー |
| 特別対応中 | Deep側が独自の追加対応を進めている | チャネル特記事項がある場合 |

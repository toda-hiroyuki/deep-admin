# リソース管理・催行回設計資料

## 1. 目的

本資料は、DeepExperience におけるリソース管理・催行回モデルの初期MVP範囲を定義するものである。

対象は以下の2区分とする。

- プライベートツアー
- グループツアー

プライベートツアーは、共通の受付条件とリソース管理を中心に整理する。

グループツアーは、受付条件・リソース管理に加えて、催行回管理および予約の催行回割当を扱う。

---

## 2. 全体方針

### 2-1. 共通方針

システムは、プライベートツアーとグループツアーに共通する受付条件として、リソース管理・最小最大人数を設定・管理できること。

MVPでは、受入可否の中心は**催行回制御**で扱い、予約制御は予約人数・予約状態・予約と催行回の紐付けを中心に扱う。

催行回と予約の紐付け状態は、予約登録設計と共通のステータス（**未紐付け / 仮紐付け / 確定紐付け**）で管理する。

### 2-2. プライベートツアー

プライベートツアーは、**1催行回 = 1予約**を原則とする。

予約が入った時点で催行回を自動作成し、即「確定紐付け」とする。そのため、未紐付け・仮紐付けはプライベートツアーでは発生しない。

### 2-3. グループツアー

グループツアーは、**1催行回 = 複数予約**を原則とする。

同一催行回に割り当てる予約は**同一ゲスト言語に限定する**。異なる言語のゲストを同じ催行回に混在させることはできない。

受付条件・リソース管理に加えて、催行回を作成・管理し、予約を催行回へ割り当てられることをMVPの中心とする。

予約が入った時点では「未紐付け」となり、運営が催行回に仮紐付けし、無料キャンセル締切後に確定紐付けへ移行する。

### 2-4. 非対象

グループツアーにおける自動再配置、自動最適化、ガイドアサイン解除を伴う再編成は、MVPの対象外とする。

---

## 3. 用語

### 3-1. 催行回

同一TourOption ID（TourOptionバージョン）・同一時間帯における、実際の催行単位をいう。ここでいう「同一TourOption」はコード一致ではなく、TourOption ID（TourOptionバージョン）一致を指す。催行回はTourOption ID（TourOptionバージョン）を必須属性で保持し、紐付く全予約は同一TourOption ID（TourOptionバージョン混在禁止）とする。

### 3-2. 催行ステータス

催行回そのものの実施状態を表すステータス。

| ステータス | 意味 |
|---|---|
| 未催行 | ツアー日前。まだ実施されていない状態 |
| Operated | 正常に催行された状態 |
| Not Operated | 予約はキャンセルされていないが催行されなかった状態。No-show・Guide_No-showが主なケース |
| Aborted | 催行途中で中断された状態。部分的な実施があった |
| Cancelled | 催行前にキャンセルされた状態 |

Not Operatedは、催行回に紐づく予約ステータスがすべてNo-showまたはGuide_No-showである場合に相当する。

Cancelled_Rescheduledは新システムでは使用しない。日時変更処理により旧催行回がCancelledになり新催行回が生成されるため、変更履歴で管理する。

### 3-3. 催行回紐付けステータス

予約と催行回の関係を表す状態。予約登録設計と共通の3段階で管理する。

| ステータス | 意味 | プライベートツアー | グループツアー |
|---|---|---|---|
| **未紐付け** | 催行回がまだ割り当てられていない | 発生しない | 予約作成直後の状態 |
| **仮紐付け** | 催行回を仮で割り当てた状態。変更可能。運営上必要な手配は進められる | 発生しない | 運営が手動で割り当てた後 |
| **確定紐付け** | 催行回への紐付けが確定し、予約の催行回変更が不可になった状態。ガイドに対して確定したゲスト情報を提供できる | 催行回自動作成と同時に遷移 | 最終確定処理後、または手動確定後 |

### 3-4. 最終確定処理

グループツアー専用の操作。

無料キャンセル締切時点で、対象日の「仮紐付け」状態の予約を一括で「確定紐付け」に移行する処理をいう。

この処理で閉じるのは既存予約の再配置であり、ガイドの確定そのものではない。なお、「確定紐付け」への移行は最終確定処理以外でも運営判断で随時可能である。

## 4. リソース管理（プライベートツアー・グループツアー共通）

リソース管理は、TourOptionの受入可否を間接的にコントロールするための仕組みである。

在庫・枠の概念に代わり、「リソース」単位で上限と消費ルールを設定する。

### 4-1. リソースとは

リソースは、TourOptionの催行に必要な物・人・設備の上限を表す単位である。

例：自転車10台、運営マンパワー3、ガイド2名、送迎車1台

1つのリソースは、複数のTourOptionで共用することも、個別TourOption専用とすることも可能である。

### 4-2. 消費単位

リソースは以下2種類の消費単位を持つ。

| 消費単位 | 説明 | 例 |
|---|---|---|
| **人数単位** | 参加人数分を消費する | 自転車、座席 |
| **催行回単位** | 催行回1回で1消費 | 運営マンパワー、チャーター車両 |

### 4-3. 利用時間（リセット周期）

リソースは、利用時間（分）を設定することでリセット周期を管理する。利用時間が経過すると、消費分がリセットされ再び利用可能となる。

| 設定例 | 利用時間 | 意味 |
|---|---|---|
| ツアー終了後に解放 | 例：180分 | ツアー所要時間に合わせて解放 |
| 1日リセット | 1440分 | 翌日に解放 |
| 週単位リセット | 10080分 | 翌週に解放 |

### 4-4. TourOptionとリソースの紐付け

TourOptionコードは商品系統の不変識別子であり、同一コードに複数のTourOptionバージョン（複数のTourOption ID）が存在しうる。コード = 商品系統の不変識別子、TourOption ID = TourOptionバージョンを一意特定する内部主キーであり、提供内容を改訂すると同一コードのまま別IDが発行され最新が現在のTourOptionバージョンとなる（一意キーはID、コードはレコード単位で重複しうる）。リソースの共有は、リソース側に複数のTourOptionコードを登録すること（§4-5の「適用TourOptionコード（複数可）」）で実現する。リソース共有は適用TourOptionコードでTourOptionバージョンをまたいで行い、リソース消費は催行回 = TourOptionバージョン（TourOption ID）単位とする。これにより、TourOptionバージョン違いや別TourOptionの間で同一リソースを共有しつつ、消費はTourOptionバージョン単位の催行回で管理できる。

在庫管理グループIDは廃止する。リソース側の適用TourOptionコード（複数可）で共有関係を管理する仕組みで代替する。

### 4-5. リソースレコード構造

| 項目 | 説明 |
|---|---|
| リソースID | 識別子 |
| リソース名 | 例：「自転車」「運営マンパワー」 |
| 消費単位 | 人数単位 or 催行回単位 |
| 上限数 | リソースの総量 |
| 利用時間（分） | リセット周期 |
| 適用TourOptionコード | 適用対象（複数可） |

### 4-6. 最小最大人数

システムは、1催行回の可能人数を管理できること。

例：1〜6名、2〜8名。

プライベートツアーでは1催行回 = 1予約となるため、結果的に1予約あたりの人数条件と一致する。

### 4-7. 予約との紐付け

システムは、予約と催行回の関係を以下の前提で扱えること。

- プライベートツアー：1催行回 = 1予約
- グループツアー：1催行回 = 複数予約

| | プライベートツアー | グループツアー |
|---|---|---|
| **リソース** | リソース側の適用TourOptionコードを通じて共有・制御 | リソース側の適用TourOptionコードを通じて共有・制御 |
| **最小最大人数** | 1催行回の可能人数（例：2〜6名） | 1催行回の可能人数（例：2〜6名） |
| **予約との紐付け** | 1催行回 = 1予約 | 1催行回 = 複数予約 |
| **催行回の作成タイミング** | 予約作成時に自動作成 | 運営が手動作成または割り当て |
| **紐付け初期状態** | 即「確定紐付け」 | 「未紐付け」から開始 |

### 4-8. 催行回制御と予約制御の役割分担

MVPでは、受入可否の中心は**催行回制御**で扱う。

**催行回制御**で主に扱うもの：

- リソース管理（上限・消費・リセット）
- 最小最大人数
- 催行回
- 催行回ごとの現在人数

**予約制御**は申込単位の情報および変更ルールを扱う（予約登録設計に詳細を定義）：

- 予約人数
- 予約状態
- 予約受付カットオフ / 無料キャンセル締切
- 予約と催行回の紐付けステータス
- 予約変更可否

予約受付カットオフ・無料キャンセル締切の**設定値はTourOptionレコードが保持**し、催行回制御・予約制御で参照して受入可否の判断に用いる。

予約人数は固定値ではなく、お客様都合で変更されうる値として扱う。予約人数が変更された場合は、紐づく催行回の現在人数に反映する。

### 4-9. 特例による上限拡張（ソフト上限のみ）

受入可否は次の3つの上限で制御する。このうち**ソフト上限（業務上限）は、運営が特定の予約・催行回に限り特例で拡張できる**。**ハード上限（物理制約）であるリソース上限は特例の対象外**とし、拡張しない。

| 上限 | 区分 | 値の出どころ | 特例拡張 |
|---|---|---|---|
| 1予約あたりの最大人数 | ソフト（業務） | 商品条件スナップショット（予約単位） | 可（当該予約のみ） |
| 1催行回あたりの最大人数＝定員 | ソフト（業務） | 催行回スナップショット（§6-2） | 可（当該催行回のみ） |
| リソース上限 | ハード（物理） | リソースレコード（§4-1〜§4-5） | 不可（免除しない） |

**スコープ（その1件だけに閉じる）**

- 催行回定員の拡張は、**当該催行回レコードのスナップショット定員のみ**を書き換える。TourOptionマスタにも他の催行回にも波及しない。
- 1予約あたり最大人数の拡張は、**当該予約の商品条件スナップショット値のみ**を上書きする。他の予約には波及しない。

いずれもインスタンス単位のスナップショット値を対象とするため、特例の影響範囲は構造的に「その1件」に閉じる。

**リソース上限は免除しない**

特例で定員を伸ばしても、リソース上限チェックは通常どおり実行し、超過する場合は受け入れない。実質の受入上限は、ソフト上限を拡張した後もリソース上限が決める。

- リソースが**人数単位**（自転車・座席など）の場合：定員を拡張してもリソース上限に空きがなければ受入不可。
- リソースが**催行回単位**（運営マンパワー・チャーター車両など）の場合：消費は催行回1回=1で人数に依らないため、定員拡張ではリソース上限に抵触しない。

**承認と記録**

特例拡張は例外承認として扱い、**理由・承認者・拡張前後の上限値**を変更・キャンセル履歴に記録する（期限後の日時変更等の例外承認と同じ運用）。

**ツアー種別による適用形**

本ルールはプライベート・グループ両方に適用するが、形が異なる。

- **グループツアー**：1催行回 = 複数予約。ソフト上限は「1予約あたり最大人数」と「催行回定員」の2つが独立して効き、それぞれ特例拡張できる。定員超過時の基本対応は「別催行回への分割／新規催行回作成」（§6-5）で、特例定員拡張は同一催行回に留める必要がある場合（同行が必要なグループ等）の例外手段。
- **プライベートツアー**：1催行回 = 1予約のため、「1予約あたり最大人数」と「催行回定員」は同一値に潰れ、催行回の現在人数は予約の参加人数に追従する（§4-7）。したがって**催行回定員を独立に拡張する操作は持たず、受入上限は「1予約あたり最大人数」のみ**として扱う。上限超過時は、1予約あたり最大人数を特例拡張したうえで人数変更（参加人数の更新。UC-03／UC-04）を行えば、催行回人数は自動的に追従する。1催行回 = 1予約のため「別催行回への分割」という代替手段は存在せず、選択肢は「特例拡張」か「お断り」の二択となる。

いずれの種別でも、リソース上限（ハード）は特例の対象外で免除しない。

### 4-10. リクエスト予約のリソース確定ゲート

リクエスト予約は受付方式（即時確定予約／リクエスト予約）の区分であり、リソース管理の有無とは独立に扱う。リクエスト予約であってもリソースを持つTourOptionがありうるため、「リクエスト予約＝リソース管理なし」とは固定しない。TourOption設定でも、受付方式とリソース設定は独立に設定できる構造とする。

リクエスト予約にリソースが設定されている場合のリソース制御は、受付時ではなく**確定時点のゲート**で行う。受付時点ではリソースに関係なくまず受け付け、確定の瞬間にリソースを判定する。

| 段階 | 予約ステータス | リソースの扱い |
|---|---|---|
| 受付時 | 確定待ち | リソースチェック・消費を行わない（まず受け付ける） |
| 確定時 | 確定予約／確定紐付け | 即時確定予約と同一のリソースチェックを実行し、上限超過なら確定不可とする |
| 確定後 | — | 催行回の現在人数に反映し、即時確定予約と同様にリソースを消費する |

確定時のリソースチェックは、即時確定予約の受入可否判定（§4-3 の時間軸占有＋§4-9 のハード上限）と同一ロジックを、予約登録時ではなく確定アクションのゲートで呼び出すものとする。チェック実行には催行回（日時）が確定している必要があるため、仮紐付け（日時確定済み）状態で確定ゲートを通す。

リソース不足による確定不可は、リソース上限がハード上限（§4-9）であることに基づき、特例拡張の対象外とする。確定操作時点で「リソース不足のため確定できない」として止める。

**仮押さえ（ソフトホールド）の非対象（将来拡張）**

MVPでは、受付時の仮押さえは行わない。したがってリソースの確保は「先に受け付けた順」ではなく「先に確定できた順」で決まる。確定待ちの間に共有リソースを即時確定予約が消費した場合、後から確定しようとしたリクエスト予約は確定できないことがある。これはリクエスト予約が「受付＝確約ではない」性質に沿った割り切りである。

受付時点でリクエスト予約にリソースを仮押さえする運用が必要になった場合に備え、確定ゲート方式は将来の仮押さえ（ソフトホールド）導入と両立する構造としておく。仮押さえ自体はMVP対象外とする。

## 5. プライベートツアー

### 5-1. 管理対象

プライベートツアーでは、以下を設定・管理対象とする。

- リソース管理
- 最小最大人数
- 催行回
- 予約との紐付け（確定紐付けのみ）

### 5-2. 基本方針

プライベートツアーでは、催行回を持つことを前提とする。

原則として1催行回 = 1予約とし、複数予約を1催行回にまとめる扱いは行わない。

予約が入った時点で催行回を自動作成し、即「確定紐付け」とする。未紐付け・仮紐付けは発生しない。

### 5-3. 最小スコープ要件

システムは、プライベートツアーについて以下を満たすこと。

- リソース管理を設定・保存・更新できること
- 最小最大人数を設定・保存・更新できること
- 催行回を自動作成できること
- 予約作成と同時に催行回を生成し、即「確定紐付け」にできること
- 1催行回 = 1予約を前提として受入可否を判断できること

---

## 6. グループツアー

### 6-1. 前提

グループツアーも、受付条件（リソース管理・最小最大人数）、催行回、予約との紐付けを持つ。

プライベートツアーが1催行回 = 1予約であるのに対し、グループツアーは1催行回 = 複数予約である。

MVPでは、まず**催行回制御**を先に実装する。そのうえで、**予約制御**は申込単位の情報および変更ルールを扱う。

予約人数が変更された場合は、紐づく催行回の現在人数に反映する。

MVPでは自動再配置は行わず、必要な場合は手動調整とする。

### 6-2. 催行回管理

システムは、予約を載せる単位として催行回を作成・管理できること。

催行回の主な管理項目：

- 催行回ID（形式 TI-…-{コード}-{連番2桁}。形式は不変で、TourOptionバージョンの区別はTourOption IDフィールドで行う）
- TourOption ID（TourOptionバージョン／束ね鍵の正本要素／必須）
- TourOptionコード（商品系統の不変識別子。TourOptionバージョンをまたいで重複しうる）
- 日時
- 定員
- 最少催行人数
- 紐づく予約
- 現在人数
- ステータス

催行回の束ね鍵は、TourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語の完全一致とする（提供内容ハッシュは不採用）。

定員・最少催行人数は、催行回作成時に当該TourOptionバージョン（TourOption ID）の値をスナップショットして保持する。TourOptionバージョン変更後も既に作成済みの催行回の定員・最少催行人数は据え置く。

### 6-3. 予約時の催行回仮紐付け

システムは、予約が入った時点では「未紐付け」とし、運営が手動で催行回を仮紐付けできること。

仮紐付けの時点では変更可能とするが、運営上必要な手配（ガイド打診など）は進められる状態とする。

### 6-4. 手動割当

システムは、運営が手動で予約の仮紐付けを設定・変更できること。

想定操作：

- 既存催行回に予約を割り当てる
- 新規催行回を作成して予約を割り当てる

### 6-5. 基本割当方針

MVPでは、以下を基本方針とする。

- 既存催行回に空きがある場合は、まず当該催行回に割り当てる
- 既存催行回に入らない場合のみ、新規催行回を作成する

### 6-6. 催行回人数管理

システムは、催行回ごとの現在人数を参照できること。

1催行回の可能人数は、**最小最大人数**で管理すること。初期設定では1催行回6名とし、変更できること。

### 6-7. 無料キャンセル締切後（最終確定処理）

無料キャンセル締切後は、その時点までに入っている既存予約の再配置を行わない（最終確定処理）。

最終確定処理の内容：

- 対象日の「仮紐付け」状態の予約を「確定紐付け」に一括移行する
- 既存予約の催行回変更を不可とする
- ただし締切後に入る新規予約については、空きのある既存催行回への追加を許容する

なお、最終確定処理で閉じるのは**既存予約の再配置**であり、ガイドの確定そのものではない。

### 6-8. 全予約キャンセル催行回の扱い

その催行回に紐づく予約が0件になった場合、当該催行回を**無効化（催行回キャンセル）**できること。

### 6-9. TourOptionバージョン分裂による催行回並立

同一TourOptionコード内で提供内容が改訂され複数のTourOptionバージョン（複数のTourOption ID）が並立すると、同一ツアー日時・同一ゲスト言語であってもTourOptionバージョン（TourOption ID）が異なる予約は、束ね鍵が一致しないため別催行回として並立する。

予約は予約作成（TourOptionバージョン解決）時点のTourOption ID（TourOptionバージョン）にピン留めされ、変更・キャンセルでも書き換えない（TourOptionバージョン固定）。インラインで新規催行回を作成する場合も、予約が保持する固定TourOptionバージョンIDを継承して生成する（その時点の最新TourOptionバージョンではない）。

TourOptionバージョン分裂で並立した各催行回について、以下は催行回ごとに独立して扱う。

- 最少催行人数の判定
- リソース消費（催行回 = TourOptionバージョン単位）
- 催行ステータス
- 予約0件時の自動Cancelled（無効化）

MVPでは並立した催行回を統合しない。OD-4=B の方針に基づき、データ上は別催行回のまま、1ガイドが両方を担当できる「手配メモ運用」での弱い共催を許容する（共催グループ概念は将来フェーズ）。

最少催行人数未達は自動中止せず、運用アラートで別途検知する（要別設計）。

## 7. グループツアー：今回実装しないもの

### 7-1. 自動再配置

- 予約追加やキャンセルに応じて、既存予約を自動で別催行回へ移すこと
- 既存予約を自動で組み替えること

### 7-2. 定期再配置

- 特定日数前に一括再配置すること
- 一定時間ごとに再配置を見直すこと

### 7-3. 自動最適化

- 利益最大化を目的とした自動再配置
- 少人数感やツアー品質を目的とした自動再配置

### 7-4. ガイドアサイン解除を伴う再編成

- 進行中のガイドアサインを見直して催行回を組み替えること
- ガイドアサイン済み催行回を前提とした高度な再編成

### 7-5. 高度な条件付き割当

- ゲスト属性や追加条件に応じた催行回選択
- 将来の予約傾向を見越した先読み割当

### 7-6. 参考：将来検討用の再配置ルール案

再配置ロジック自体はMVP対象外とする。将来検討事項として、タイミングごとの再配置判断ルール案を以下に示す。

1. **ツアーの3日以前**：ガイドアサイン優先。1つでも予約が残る催行回はそのまま残す
2. **ツアーの3日前になった時**：利益重視。この時点で1回だけ再配置する
3. **ツアーの3日前 〜 無料キャンセル締切前**：利益重視。12時間置きに再配置を見直す
4. **無料キャンセル締切後**：既存予約の再配置はしない

## 8. 要件一覧

### 8-1. MVP実装対象

**共通（プライベートツアー・グループツアー）**

- リソース管理を設定・管理できること（消費単位 / 上限数 / 利用時間 / 適用TourOptionコード）
- 最小最大人数を設定・管理できること
- 予約との紐付け方を区分ごとに扱えること
- 商品によってはリソース設定なし（無制限相当）を許容できること
- リソース側に複数のTourOptionコードを登録することで、複数TourOption間で同一リソースを共有できること

**プライベートツアー**

- リソース管理・最小最大人数を用いて受入可否を判断できること
- 予約作成時に催行回を自動作成し、即「確定紐付け」にできること
- 1催行回 = 1予約を前提とすること
- 催行回への複雑な割当や再配置を前提としないこと

**グループツアー**

- 催行回を作成・管理できること
- 予約が入った時点で「未紐付け」とし、運営が手動で催行回を仮紐付けできること
- 手動で仮紐付けを設定・変更できること
- 既存催行回に空きがある場合は、まず当該催行回へ割り当てること
- 既存催行回に入らない場合のみ、新規催行回を作成すること
- 催行回ごとの現在人数を参照できること
- 1催行回の可能人数を最小最大人数として管理できること
- 催行回に紐づく予約が0件になった場合、無効化できること
- 無料キャンセル締切後の最終確定処理（仮紐付け → 確定紐付けへの一括移行）ができること
- 無料キャンセル締切後は、既存予約の再配置を行わないこと
- 無料キャンセル締切後に入る新規予約については、空きのある既存催行回への追加を許容すること
- 予約人数が変更された場合、紐づく催行回の現在人数に反映できること

### 8-2. MVP実装対象外

**グループツアー**

- 予約追加やキャンセルに応じた自動再配置
- 既存予約の自動組み替え
- 一定日数前・一定時間ごとの定期再配置
- 利益最大化・ツアー品質を目的とした自動最適化
- ガイドアサイン解除を伴う再編成
- ゲスト属性や追加条件に応じた高度な催行回選択
- 将来の予約傾向を見越した先読み割当

### 8-3. 運用前提

- グループツアーでは、複数予約が同一催行回に載ることを前提とする
- MVPでは、受入可否の中心は催行回制御で扱う
- 予約受付カットオフ・無料キャンセル締切の設定値はTourOptionレコードが保持し、催行回制御・予約制御が参照する
- 予約人数は変更可能な値として扱い、変更時は紐づく催行回の現在人数に反映する
- グループツアーのMVPでは、予約時に「未紐付け」とし、運営が手動で仮紐付けする
- 仮紐付けを前提に、ガイド打診や手配準備を進める
- 最終確定処理で閉じるのは既存予約の再配置であり、ガイドの確定そのものではない
- 調整が必要になった場合、MVPでは自動再配置ではなく手動調整で対応する

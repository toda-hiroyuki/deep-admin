- 作成: 2026-06-12
- 対象: `deep-experience-html/admin/` のHTMLプロトタイプ一式 ＋ 設計資料(ルート直下の各 `*.md`)
- 目的: プロトタイプと設計資料を実装する際に、**機能と目的を取り違えないための「最初に読む1枚」**。ここに全体像・横断ルール・確定方針・プロトタイプの落とし穴を集約する。

## 0. まず押さえること（成果物の位置づけ）

- **HTMLプロトタイプ = 画面構成・UIフロー・項目の参考**。ロジックの一部とサンプルデータは説明用で、実装の正本ではない。
- **業務ルールの正本は設計資料(`*.md`)**。画面の挙動と資料が食い違う場合は資料が優先（本メモ §3 で個別指示する箇所を除く）。
- **正準の優先順位**: ①本メモ ②各設計資料 ③HTMLプロトタイプ ④サンプルデータ。
- `admin/` と `admin_toda/` の関係:
  - `admin/` = 全画面のプロトタイプ（今回レビュー・修正した対象）。
  - `admin_toda/` = TourOption・商品ページ・**ツアー行程**・チャネル系を開発メンバーが作り直した版。**それらの画面は admin_toda を優先**。§3-E はそちら向けの注意。
- `〇〇 (standalone).html` は配布用の自己完結版で中身は同等だが、**古い版が混じる場合がある**。現行は単体 `〇〇.html` を正とする。`bundle_src.html` / `*.jsx` / `data.js` は旧ビルド素材で、現行の単体HTMLが正。

## 1. 横断ルール（ID・マスタ・金額）

### 1-1. ID形式（全画面共通）
| 種別 | 形式 | 例 | 備考 |
|---|---|---|---|
| 予約ID | `BK-YYMMDD-XXXXX` | `BK-260601-00002` | **YYMMDD = 予約受付日**（登録が遅れた場合は実際の受付日）。ツアー日ではない。連番は日付ごとに独立採番 |
| 催行回ID | `TI-YYYYMMDD-HHMM-{TourOptionコード}-{連番2桁}` | `TI-20260615-0900-G-WAK-001-2-GR-01` | 日付・時刻部は催行回のツアー日時と一致 |
| TourOptionコード | `{PJ}-{地域}-{主番3桁}-{枝番1桁}-{商品種類}` | `G-WAK-001-2-PR` | PJ=D(Deep受託)/X(DeepX)/G(Add)。商品種類=GR/PR/CU。番号は主番-枝番（枝番=派生商品、TourOptionバージョンではない）。**TourOptionバージョンはコードに含めず、改訂版は同一コードで別レコード（別ID）。コードは商品系統を識別** |
| ガイドID | `G-{NNN}` | `G-001`, `G-1000` | 3桁ゼロ埋め、1000以上はそのまま。変更不可。**内部IDとコードを分けない（1フィールド）** |

- TourOptionコードの先頭は**PJ（プロジェクト区分）**: `D`=Deep受託 / `X`=DeepX / `G`=Add（既存サンプルは `G-` 始まり、実データは `D-` もある）。**TourOptionバージョンはコードに含めない**（提供内容を改訂したら同一コードで別TourOptionレコード＝別ID を作り、最新を現在のTourOptionバージョンとする）。番号は主番3桁-枝番1桁で、枝番は同テーマの派生商品（TourOptionバージョンではない）。
- **地域コードは47都道府県マスターで固定**（3〜4文字・半角英大文字、現状は全て3レター）。正本 = 「商品・販売設計資料.md 地域コードマスター（都道府県）」。よく使う例: 東京=`TOK`（`TKY`は誤り）/ 京都=`KYO` / 大阪=`OSK` / 石川=`ISK` / 福井=`FKI`。発音の近い県は区別のため変則表記（宮城MYG↔宮崎MYZ、山形YMT↔山口YMC 等）。

## 2. 誤解しやすい業務ルール（確定済み・正準）

分岐を読み違えやすい点。すべて設計資料に反映済みだが重要なので再掲。

1. **全件キャンセル時のガイド手配**（変更・キャンセル設計資料 §7-4）
   - 催行回の残存有効予約が **0件（催行回 Cancelled）→ ガイド手配を「キャンセル」＋通知要否フラグON**。
   - **1件以上残る（催行回存続）→ ガイド手配を維持＋再手配要否フラグON**。
   - ⚠ 無条件で「キャンセル」にしないこと（グループで他予約が残るのに手配を消すと事故）。

2. **日時変更の受付ゲート**（変更・キャンセル設計資料 §5-1/§5-2）
   - 受付条件 = TourOptionの「日程変更可否」がON **かつ 無料キャンセル期限内**。
   - **このゲートはゲスト都合の日時変更のみに適用**。運営都合・第三者都合(OTA等)は対象外。
   - 期限経過後にゲストが希望した場合はキャンセル＋新規予約として案内。例外承認時は理由を記録。

3. **適用時給はアサイン時に入力・記録**（ガイド手配設計資料 §7-1/§7-2）
   - アサイン操作時に**基本時給を初期表示**して入力。ガイド確認による確定時点でその値が確定値になる。

4. **ガイド精算の差戻し（MVP対象）**（ガイド手配設計資料 §14-5）
   - 差戻し操作あり。差戻すと精算ステータスは「実績入力待ち」に戻る。

5. **催行回の単独新規作成画面は作らない**（運営管理 §3-3）
   - 催行回の新規作成は「予約割り当て時のインライン作成」のみ（予約割り当て画面、または予約詳細の割り当て操作）。確定紐付けへの切替は催行回詳細で行う。

6. **収支集計は「金額確認待ち」を除外**（売上・原価管理 §10）
   - 取込予約のうち金額未確認のものは収支一覧の集計に含めない。除外件数を画面に出し、金額確認待ち一覧へ誘導する。

7. **予約一覧・予約詳細の画面要件の正本 = 運営管理画面設計資料＋現行HTML**
   - 予約登録設計資料 §20 の超過要件（運営確認ステータス列・商品条件スナップショット表示・監査ログ・参照URL管理など）は**将来フェーズ**。MVPでは作らない。

## 3. プロトタイプが矛盾／省略している箇所と正準の意図 ★最重要

プロトタイプを鵜呑みにすると実装を誤る箇所。資料は修正済みだが、プロトタイプ側に残るギャップを明示する。

### A. 催行ステータスは5値（催行回詳細の画面が3値しかない）
- **プロトタイプの状態**: 催行回詳細.html は `未催行 / 催行済み / 中止` の3値トグルのみ。
- **正準**: 催行ステータスは **5値 = 未催行 / Operated(催行済み) / Not Operated(不催行) / Aborted(中断) / Cancelled(中止)**（リソース管理・催行回設計資料、運営管理 §2-1）。
- **実装メモ**: Not Operated・Aborted を必ずモデルに含める。3値で実装しない。催行回一覧は5値で表示済みなのでそちらの語彙に合わせる。

### B. 催行回レベルの「手配状況」は6ラベル【確定済み】
- **正準（確定）**: **未手配 / 募集中 / アサイン済み / 一部確定 / 確定済み / 要確認**（運営管理 §2-1、ガイド手配 §6-1 を一致させ済み）。
  - 「アサイン済み」= 直接アサイン済み or 応募からアサイン済みで**ガイド確認待ち・確定0件**の状態（解除可能なウィンドウ）。
  - 「募集中」はアサイン済みを含めない（募集中のみ・確定0件・アサイン済み0件）。
- **実装メモ**: 「アサイン済み」を独立した状態として持つ。旧資料で5ラベル（アサイン済みを募集中に包含）だった記述は修正済み。

### C. 「個別単価」は専用レコードを持たない【確定済み】
- **状態**: ガイド手配操作・精算確認で「個別単価」表記が出るが、保持方法が曖昧だった。
- **正準（確定）**: ガイドマスタが持つ報酬は**基本時給1本**。特定TourOptionで基本時給と異なる単価が必要な場合は、**アサイン時に運営が「適用時給」を手動で上書き**する運用。個別単価の専用レコードは作らない。
- **実装メモ**: ガイド×TourOptionの単価マスタは不要。アサイン画面で適用時給を編集可能にすればよい。プロトタイプの「¥3,800(個別単価)」表記は手動上書きの結果という解釈。

### D. 催行回マッチング鍵 = TourOption ID（TourOptionバージョン）＋ツアー日時＋言語の完全一致【確定済み（2026-06-15）】
- **状態**: 予約割り当て.html は催行回候補を「同一TourOption(枝番まで)・同一ツアー日時・同一言語・**提供内容ハッシュ完全一致**」で絞るが、提供内容ハッシュは**不採用**で確定。
- **正準（確定・2026-06-15）**: 束ね鍵 = **TourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語の完全一致**。提供内容ハッシュは**不採用**（廃止）。
  - 「同一TourOption」表記は **「同一TourOption ID（TourOptionバージョン一致）」** の意味（コード一致ではない）。コードは商品系統の不変識別子で、改訂版は同一コードで別ID（レコード単位で重複しうる）。一意キー＝ID。束ね鍵の正は **TourOption ID**。
  - 予約はTourOption ID（TourOptionバージョン）と商品条件スナップショットID（予約時点スナップショット）の両方を保持するが、束ね鍵に使うのは **TourOption ID** のみ。商品条件スナップショットIDは金額・ポリシー再現専用で束ね鍵に使わない。
  - 催行回レコードはTourOption ID（TourOptionバージョン）を必須属性で保持し、紐付く全予約は同一TourOption ID（TourOptionバージョン混在禁止）。
- **開発メンバー申し送り（実装撤去）**: 予約割り当て.html の**提供内容ハッシュ実装は撤去**し、候補絞り込みを **TourOption ID 一致**（＋ツアー日時＋言語の完全一致）へ置換すること。ハッシュ生成・比較ロジックは実装しない。
- **下記1〜3は決定済み（§4参照）**:
  1. 提供内容（行程・集合解散・所要時間・含まれるもの・**定員/最少催行人数**）は **TourOption（TourOptionバージョン）固定**（催行回ごとの上書き不可）＝OD-2=A 決定済み。
  2. TourOptionバージョンの増分トリガーは **提供内容の実体改訂時のみ**（価格・販売条件・キャンセルポリシーは同一ID内の有効期間付き子レコードで管理しTourOptionバージョンを増やさない）＝OD-1=A 決定済み。
  3. マッチング鍵は **TourOption ID（TourOptionバージョン）＋日時＋言語の完全一致**で確定（提供内容ハッシュ不採用）。

### E. (admin_toda) TourOption販売ステータスとチャネルURL — プロトタイプが自己矛盾
- **E-1 販売ステータス**: プロトタイプは `掲載中 / 非公開 / 下書き` の3値だが、「販売ステータスが『一時停止』のときのみ必須」という販売停止理由フィールドが残っている（遷移不能）。
  - **正準**: TourOptionの販売ステータスは **5値 = 下書き / 販売準備完了 / 販売中 / 一時停止 / 終了**（商品・販売設計 §11）。「掲載中/非公開」は**商品ページ側の掲載ステータス**の語彙で別概念。混同しない。
- **E-2 チャネル別掲載URL**: プロトタイプに有効/無効トグル（`enabled`）が残るが、同画面のInfoNoteは「販売停止時はレコードを削除」と案内していて矛盾。
  - **正準**: チャネル別掲載URLレコードに**有効/無効フラグは持たない**。販売停止時はレコードを削除する運用。`enabled` フィールドは実装しない。
- **E-3 1催行回あたりの最小人数**: プロトタイプ（admin_toda の TourOption編集）に「1予約あたり最小/最大人数」はあるが「**1催行回あたりの最小人数（最少催行人数）**」の入力欄がない。

## 5. プロトタイプのデモ限定要素（実装対象外）

- **サンプルデータの具体値**（予約・ガイド・金額・日付）は説明用。データモデルと計算ロジックだけ参照する。
- **シナリオバー / トグル**（期限内/期限後、銀行差異あり/なし 等）はデモ切替用UI。本番には出さない。
- **一部のボタンがトースト表示のみ**で遷移しない箇所が残る場合がある（主要導線は実リンク化済み）。遷移先は画面名から判断。
- **ダッシュボード**はナビ項目があるがMVP対象外（プレースホルダ）。
- プロトタイプが**分岐を省略している機能**（追加請求未払い時の3択＝取消/未収維持/免除、増員時の定員チェック＝画面上は常に「確保可能」、変更・キャンセル処理のプライベート/グループ差）は**設計資料に記載あり**。見た目ではなく資料の分岐に従って実装する。

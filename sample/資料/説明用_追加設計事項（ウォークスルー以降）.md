## A. 前提として次回まず説明したい：TourOptionバージョン と 商品条件スナップショット

ウォークスルー §0-4 に記載済み。**未説明のためここで再掲**。B-1（特例拡張）が「商品条件スナップショットの1予約あたり最大人数」「催行回スナップショットの定員」を直接の操作対象にするので、この二層理解が後続の前提になる。

**用語の二層（混同禁止）**

| 層 | 用語 | 実体 | 束ね鍵か |
|---|---|---|---|
| L1 | **TourOptionバージョン**（＝TourOption ID） | 提供内容の改訂版。複数予約・複数催行回が共有 | **○（正）** |
| L2 | **商品条件スナップショット** | 予約成立時点の価格／ポリシー／行程のスナップショット。予約1件＝1レコード | ×（金額・ポリシー再現専用） |

要点：

- 予約は TourOption ID と 商品条件スナップショットID の両方を保持するが、**催行回の束ね鍵は TourOption ID のみ**（L2は催行回間で一致しないため使わない）。
- **コードはバージョンを持たない**。改訂版は同一コードの別ID。`コード一致を束ね鍵にしてはいけない`。催行回マッチング＝**TourOption ID ＋ ツアー日時 ＋ ゲスト言語の完全一致**。
- OD-1〜OD-6の整理（2026-06-15時点。新バージョンは提供内容の実体改訂時のみ／価格・ポリシーは同一ID内の有効期間子レコード／引き直しはMVP対象外／弱い共催は手配メモ運用／同一コード内は販売中1件強制／必要画面のみ可読ラベル補助表示）。
- 最大リスク＝**TourOptionバージョン分裂**（同日時・同言語の客が版ごとに別催行回へ強制分割→催行不成立・二重手配）。

## B. ウォークスルー以降に設計資料へ追加した内容（6項目）

### B-1. 特例による上限拡張（ソフト上限のみ）＝新設 §4-9
出典: **リソース管理・催行回設計資料 §4-9（新設）**

受入可否を決める上限を3つに整理し、**ソフト（業務）上限だけは運営が特例で拡張可、ハード（物理＝リソース上限）は拡張不可**と整理した。

| 上限 | 区分 | 値の出どころ | 特例拡張 |
|---|---|---|---|
| 1予約あたり最大人数 | ソフト | 商品条件スナップショット（予約単位） | 可（当該予約のみ） |
| 催行回定員 | ソフト | 催行回スナップショット | 可（当該催行回のみ） |
| リソース上限 | ハード | リソースレコード | **不可（免除しない）** |

説明ポイント：

- **影響範囲はその1件に閉じる**。定員拡張は当該催行回スナップショットのみ、1予約上限拡張は当該予約スナップショットのみを書き換え、TourOptionマスタや他レコードに波及しない。
- **リソース上限は必ず別途ゲート**。定員を伸ばしてもリソースに空きがなければ受入不可。人数単位リソース（自転車・座席）は効く／催行回単位リソース（マンパワー・チャーター車）は1催行回=1消費で定員拡張の影響を受けない。
- **承認・記録**: 例外承認として理由・承認者・拡張前後の上限値を変更・キャンセル履歴に記録。
- **種別差**: グループは「1予約上限」と「催行回定員」が独立し各々拡張可（基本は分割／新規催行回、特例は同一催行回に留める例外手段）。プライベートは1催行回=1予約で両上限が同値に潰れ、**操作は「1予約上限の拡張」のみ／分割という代替がなく「特例拡張かお断り」の二択**。

### B-2. 増員フロー（UC-03・増6）への特例拡張分岐の反映
出典: **変更・キャンセル_ユースケース UC-03 / 全条件別フロー分析 増6**

B-1を増員ユースケースに織り込み、定員超過時の選択肢を更新した。

- 増6（グループ・催行回定員超過）を「処理不可」から **「不可 / 別催行回へ分割 / 特例拡張」** の3択に変更。特例拡張・分割でメインフローに復帰しうる。
- 一方 **増5（リソース上限超過＝ハード）は従来どおり処理不可**。「特例拡張はソフト上限のみ、リソース上限は手順4で別途ゲート」を明記。

### B-3. OTAペナルティ（運営都合違約金）の原価計上を一本化
出典: **ガイド手配設計資料 §10-4 / 支払い・決済管理 §4-1 / 全条件別フロー分析**

運営都合キャンセルでOTAから課される違約金の扱いを整理。

- ガイド手配 §10-4「運営費精算」に**独立科目「OTAペナルティ（運営都合違約金）」＋備考を新設**。チャネル手数料とは別の原価として粗利から差し引く。
- **原価計上は運営費精算側に一本化**。支払い側・変更／キャンセルレコードには重複計上しない。支払いステータス「Penalty Applied」は**状態の表現に留め、原価を持たせない**（二重計上防止）。
- 移行: 稼働後の新規は§10-4独立科目で記録／既存で分離可なら振り分け／分離不可なら手数料込みのまま「手数料ペナルティ込み（移行）」フラグ付与（手数料率分析時は除外）。

### B-4. 支払いステータスは「登録時4値／登録後に9値」
出典: **予約登録 設計資料 / 運営管理 §2-1**

支払いステータスの正式値セットは9値だが、**予約登録時点では4値（未払い / 支払い済み / 支払い不要 / 要確認）のみ選択可**と整理。返金・係争・分割入金・ペナルティ系（Partially Paid / 部分返金済み / 全額返金済み / Chargeback・Disputed / Penalty Applied）は**登録後に入金照合・返金処理等を経て更新**する。

### B-5. グループツアーのガイド報酬を人数按分で月次配賦
出典: **売上・原価管理設計資料 §6-2**

グループツアー（複数予約が1催行回を共有）の原価配賦方針を更新。**記録粒度＝催行回単位／表示粒度＝予約別**を分けて扱うことを明示。

- **ガイド報酬**: 催行回単位で発生するが、**月次の予約別表示では人数按分（予約人数 ÷ 催行回合計人数）で配賦表示**（MVPで対応済みに変更）。
- **施設費（固定）**: 従来どおり催行回単位で記録、予約単位への配賦はMVP後に決定（将来拡張から「ガイド報酬を除く」と修正）。

### B-6. 増員時の追加請求ステータス（AC_STATUS）新設＋返金ステータスの責務分界
出典: **運営管理 §3-11-2（人数変更処理）**

- **追加請求ステータス（AC_STATUS）を新設**（増員・直販扱いのOTA当日現地増員で追加請求が出る場合の決済リンク発行〜回収管理）。5値＝**未送付 / 請求済み（未払い）/ 支払い済み / 期限切れ / 取消**。OTA経由の通常増員はOTA次回精算で調整するため対象外。
- **返金ステータス（§2-1の6値）の責務分界を明確化**: 6値は減員・キャンセルの処理結果として作られた返金レコードの進捗管理で、その表示・更新は**変更・キャンセル履歴／予約詳細（§3-8）側の責務**。変更・キャンセル処理画面は**返金額の確定までを扱い、6値の遷移管理は行わない**。

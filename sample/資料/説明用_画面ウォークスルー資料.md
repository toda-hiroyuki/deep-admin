# 説明用 画面ウォークスルー資料（運用系画面）

- 作成: 2026-06-15
- 対象: `deep-experience-html/admin/` のうち、**戸田さんに未提供の運用系画面**（予約オペレーション / ガイド管理 / 精算・経営）
- 目的: 運用系HTMLプロトタイプを **読んで把握するための資料**。各画面が「なぜ存在し・何をする画面で・どこに注意すべきか」を、案件のライフサイクル順に1枚へまとめる。
- 併読: 機能の正本は各設計資料（本資料は各画面で管轄資料を明記）。プロトタイプの落とし穴は『開発向けハンドオフメモ』§3 を参照。
- 読み方（凡例）: 各画面は おおむね **役割 / 主な機能 / 導線 / 重要ポイント / 落とし穴** の順で記載（項目は画面により増減）。**管轄** に挙げた設計資料がその画面の機能の正本。**★** は最重要画面。「**ハンドオフメモ §x**」はプロトタイプと設計仕様の差異・確定方針の参照先。
- プロトタイプの開き方: [_全画面ビュー.html](../_全画面ビュー.html) を開き、左サイドバーから画面を切り替えると、単体HTMLを個別に開かずに本資料の順序どおり確認できる。
- 注意: プロトのシナリオバー・トグル等の切替UIは**デモ専用**で、本番画面には出ない（確認用の操作）。

## 0. 前提と全体像

### 0-2. 全体像：案件のライフサイクル

運用系画面は機能の羅列ではなく、**1件の予約が生まれてから精算・入金されるまでの流れ**で並ぶ。各画面が「なぜ存在し、どこに繋がるか」はこの流れで捉えると分かりやすい。下図の流れ＝本資料の構成順。

```
【前提】商品設計（戸田済み）
  TourOption → 商品ページ → 催行回マスタ
        │
        ▼
① 予約が発生         予約登録 / OTA取込 → 予約一覧 → 予約詳細（操作ハブ）
        │
        ▼
② 催行回へ割り当て    未割り当て一覧 → 予約割り当て →（催行回詳細で確定紐付け）
        │
        ▼
③ ガイドを手配        〔ガイドマスタ〕→ 未手配一覧 → ガイド手配操作 → 応募者一覧
        │
        ▼
④ 当日運営            当日/翌日案件一覧（直前アラート）
        │
   （随時）変更・キャンセル処理  ← ライフサイクル横断
        │
        ▼
⑤ ツアー後・精算      精算確認 → 金額確認待ち一覧
        │
        ▼
⑥ 入金・経営          OTA入金照合 → 収支一覧 → 月次締め確認 →〔チャネル・手数料設定〕
```

### 0-3. 背骨は「5系統のステータス」

各画面は独立して動くのではなく、**5系統のステータスが連動して遷移**することで案件が前に進む。各画面は「このステータスをこう変える画面」と捉えると位置づけが掴める（正本: 運営管理画面設計資料 §2-2）。

```
[予約]   確定待ち → 確定予約 →（実施後）Completed / No-show ほか
[紐付け] 未紐付け → 仮紐付け → 確定紐付け
[手配]   未手配 → 募集中 → アサイン済み → 一部確定 / 確定済み
[催行]   未催行 → Operated / Not Operated / Aborted / Cancelled（5値）
[精算]   見込み設定済み → 実績入力待ち → 確認待ち → 確定
```

> 画面数は約20だが、本質は **“この5系統のステータスを正しく前へ進める”** 操作の集合。個々の画面はその一手段と捉えると全体が掴める。

### 0-4. TourOptionバージョンと催行回マッチング（束ね鍵の中核・最重要）

予約割り当て・催行回・収支に共通して効く中核概念。**用語の二層**と**催行回の束ね鍵**を取り違えると設計が崩れる（正本: 商品・販売設計資料 §5・§15／ハンドオフ §3-D。2026-06-15に OD-1〜OD-6 で全確定）。

**(1) 用語の二層（混同禁止）**

| 層 | 用語 | 実体 | 用途 | 束ね鍵か |
|---|---|---|---|---|
| L1 | **TourOptionバージョン**（＝TourOption ID） | 提供内容の改訂版。同一コードを共有する改訂レコード（本物の「バージョン」）。複数予約・複数催行回が共有 | **催行回の束ね・同乗可否判定の正本** | **○（正）** |
| L2 | **商品条件スナップショット**（＝商品条件スナップショットID） | 予約成立時点の予約時点スナップショット（価格/ポリシー/行程）。予約1件＝1レコード | 金額・ポリシーの当時条件再現専用 | ×（参照専用） |

- 予約は **TourOption ID と 商品条件スナップショットID の両方を保持**するが、**束ね鍵に使うのは TourOption ID のみ**（L2は催行回間で一致しえないため束ね鍵にしない）。
- 旧称の対応: 旧「版」＝L1 TourOptionバージョン／旧「商品バージョン」＝L2 商品条件スナップショット。

**(2) TourOptionコード書式（バージョンではない）**

- 書式＝`{区分}-{地域3}-{番号3}-{枝番}-{種別}`（例 `G-WAK-001-2-PR`）。4番目は**枝番**＝同テーマの派生商品で、**バージョンではない**。
- **コードはバージョンを持たない**。改訂版は**同一コードの別ID**（＝TourOption IDが変わる）。よってコードはレコード単位で重複しうり、一意キーはID。**「コード一致」を束ね鍵にしてはいけない**。

**(3) 催行回マッチング＝TourOptionバージョン一致への一本化**

- 束ね鍵＝**TourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語の完全一致**（コード一致ではない）。
- 催行回レコードは TourOption ID を必須属性で保持し、紐付く全予約は同一TourOption ID（**バージョン混在禁止**）。
- 予約は**予約作成（バージョン解決）時点でTourOption ID（バージョン）にピン留め**し、変更・キャンセルでも書き換えない。日時変更差額＝現在の版価格 vs 予約時点スナップショット価格／キャンセル料＝予約時点ポリシー×判定日時。

**(4) TourOptionバージョン管理の確定事項（OD-1〜OD-6。OD＝Open Decision＝要判断事項）**

| ID | 確定 |
|---|---|
| OD-1 | 新TourOptionバージョンは**提供内容の実体改訂時のみ**。価格・販売条件・キャンセルポリシーは同一ID内の有効期間付き子レコードで管理しTourOptionバージョンを増やさない |
| OD-2 | 提供内容は**TourOptionバージョン固定**。催行回ごとの上書き不可 |
| OD-3 | バージョン**引き直し（旧TourOptionバージョン→新TourOptionバージョン付け替え）はMVP対象外**（TourOption変更扱い） |
| OD-4 | TourOptionバージョン分裂で並立した催行回は、1ガイドが両方を担当する**「手配メモ運用」の弱い共催**を許容（共催グループは将来フェーズ） |
| OD-5 | 同一コード内で**販売中＝1件強制**。新TourOptionバージョンを販売中へ昇格した瞬間、旧TourOptionバージョンを「新規受付停止」へ自動遷移＋子レコード自動継承 |
| OD-6 | 必要画面（割り当て/催行回詳細/予約詳細）に限り、**人間可読のTourOptionバージョンラベル（連番・発効日）を補助表示**。一覧の常時列・生ID表示はしない |

**(5) 最大リスク＝TourOptionバージョン分裂（要警告）**

- 商品改訂で**同日・同時刻・同言語の客がTourOptionバージョンごとに別催行回へ強制分割**される。最少催行人数未達による催行不成立・ガイド二重手配・リソース二重消費を招く構造的副作用。
- 対処＝OD-1（新TourOptionバージョン頻度を最小化）＋OD-4（手配メモ共催）＋OD-6（「同一コード・同一日時・同一言語だがバージョンが異なるため同乗不可」を可視化）。最少催行人数の自動中止はMVP対象外（運用アラートで代替）。

## ① 予約オペレーション（入口〜割り当て）

### ① -1. 予約登録
- **HTML**: [予約登録.html](../予約登録.html) ／ **管轄**: 予約登録 設計資料
- **役割**: OTA取込・問い合わせ・電話など、自社サイト以外の予約を手動でシステムに載せる入口。
- **主な機能**:
  - チャネル / 予約元の選択、外部予約番号の入力。
  - TourOption・ツアー日時・参加人数・ゲスト情報・集合/ピックアップ・販売金額の登録。
  - 予約受付方式（即時確定 / リクエスト）→ 予約ステータスの初期値（確定予約 / 確定待ち）が決まる。
- **導線**: 登録完了 → 予約詳細／予約一覧に出現。
- **重要ポイント**: 予約IDは `BK-YYMMDD-XXXXX`（YYMMDD=**予約受付日**、ツアー日ではない）。販売金額＝グロス売上の基準（OTAレポート額ではない）。
- **落とし穴**: ハンドオフメモ §2-7 — 予約登録設計資料 §20 が挙げる予約詳細画面の**追加表示UI**（運営確認ステータス列・商品条件スナップショットの画面表示・監査ログ表示等）は**将来フェーズ**で、MVPの予約詳細画面には出さない。**ただし商品条件スナップショット（L2＝予約成立時点の価格/ポリシー/行程のスナップショット・金額/ポリシー再現専用）の生成・紐付け自体は予約成立時に必ず行う＝MVP**（§9・§15）。将来フェーズなのは「作る/作らない」ではなく予約詳細画面での**表示**の範囲。なおデータ不備タブの「運営確認ステータス列」は運営の確認進捗（未確認/確認中/要対応 ほか）を管理するMVP要素（運営管理§2-1）。§20で将来扱いなのは全予約タブの常時列表示・予約詳細での編集UIの方。

### ① -2. 予約一覧
- **HTML**: [予約一覧.html](../予約一覧.html) ／ **管轄**: 運営管理 §3-1
- **役割**: 全予約を俯瞰し、対応が必要な案件を素早く特定する起点。
- **タブ構成（4タブ）**:
  - **全予約**: 通常の予約一覧。列＝予約ID / 予約日 / ゲスト名 / TourOption / ツアー日時 / 人数 / チャネル / 予約ステータス / 催行回紐付け / 手配状況 / データ不備フラグ。
  - **データ不備**: システムが**自動付与**したデータ不備フラグの立つ予約を抽出。運営は内容を確認・修正のうえ「確認済みにする」でフラグを解除（自動付与のため**手動でフラグを立てるボタンは無い**＝旧「要確認フラグを立てる」は廃止）。旧称「要確認タブ」を「データ不備」に改称済み。
  - **重複疑い**: 重複ペア判定にかかった予約を抽出（同一ゲスト・同一日時の二重取込等）。
  - **取込ログ**: OTA / Bokun 等の取込結果ログ。列＝取込日時 / 取込元システム / 販売チャネル / 外部予約番号 / 処理結果 / 内容 / 社内予約ID / 操作。操作列は**「予約未生成の取込失敗（社内予約ID無し）」の行のみ「手動登録」リンク**を表示し予約登録へ誘導（社内予約ID有りの行は「—」）。
- **主な機能（全予約タブ）**:
  - 絞り込み: 予約ID・外部予約番号（問い合わせ対応の即特定）/ ステータス / ツアー日 / 予約日 / TourOption / チャネル / 手配状況 / データ不備。
  - ソート: ツアー日時・予約日。デフォルトはツアー日時昇順。
- **導線**: 行クリック → 予約詳細。取込ログの社内予約IDリンク → 予約詳細／手動登録リンク → 予約登録。
- **重要ポイント**: ここに出る「催行回紐付け」「手配状況」列が、②③へ進むべき案件のシグナル。データ不備フラグは**システム自動付与**（OTA取込のTourOption解決失敗・公開中TourOptionバージョン取得失敗・必須項目欠落等）であり、運営が立てるものではない。

### ① -3. 予約詳細 ★最重要（操作ハブ）
- **HTML**: [予約詳細.html](../予約詳細.html) ／ **管轄**: 運営管理 §3-8
- **役割**: 1予約の全情報を集約し、**後続の全操作（割り当て・手配・変更/キャンセル・返金）の起点**になる中心画面。この画面を起点に把握すると、他画面の位置づけが繋がる。
- **主な機能（セクション）**:
  - ① ヘッダー: 予約/支払い/紐付けステータスのバッジ、データ不備フラグ、アクション（変更・キャンセル処理 / ガイド手配操作 / 外部予約管理画面）。
  - ① 補足: 催行回紐付け操作（グループのみ）— 未紐付け「割り当てる」／仮紐付け「変更する・確定紐付けにする」。
  - ② 予約基本情報: TourOption・日時・人数は**直接編集不可**（変更・キャンセル処理から）。チャネル・外部予約番号は直接編集可。
  - ③ ゲスト情報 / ④ 集合・ピックアップ: 直接編集可、保存時に変更履歴を記録。
  - ⑤ ガイド手配情報: 手配状況・担当ガイド・再手配要否フラグ →「手配操作を開く」。
  - ⑥ 支払いサマリー: 販売金額・入金・返金/追加請求 →「返金処理を記録」。
  - ⑦ 変更・キャンセル履歴 → 「変更・キャンセル処理を行う」。
  - ⑧ 社内メモ（ガイド非公開）/ ガイド共有メモ。
- **重要ポイント**: 「日時・人数・TourOption は詳細画面から直接いじれず、必ず変更・キャンセル処理を通す」= 履歴と金額・再手配への波及を漏らさないための設計。

## ② 催行回への割り当て

### ② -1. 未割り当て一覧
- **HTML**: [未割り当て一覧.html](../未割り当て一覧.html) ／ **管轄**: 運営管理 §3-2
- **役割**: 催行回未紐付け（＝「未紐付け」）の予約を抽出し、割り当て漏れを防ぐ。割り当て後は一覧から外れる。
- **主な機能**: 予約単位の表示、ツアー日時昇順、各行「割り当て」→ 予約割り当てへ。
- **重要ポイント**: 表示単位は**予約単位**（次の催行回一覧は催行回単位）。混同しないよう注意。

### ② -2. 予約割り当て
- **HTML**: [予約割り当て.html](../予約割り当て.html) ／ **管轄**: 運営管理 §3-3
- **役割**: 未紐付け予約を催行回へ**仮紐付け**する。
- **主な機能（2方式）**:
  - (a) 既存催行回に紐付け: 束ね鍵＝**TourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語の完全一致**する回のみ候補。枠不足の回は選択不可（空き枠ゲートは束ね鍵とは独立して維持）。
  - (b) 新規催行回をインライン作成: 既存に入らない場合のみ。**TourOption ID（＝予約の固定TourOptionバージョン）と言語を予約から継承**（現時点の最新TourOptionバージョンではない・変更不可）、日時を入力、定員は当該TourOptionバージョンの設定値をスナップショット初期表示。作成と同時に仮紐付け。
- **重要ポイント / 落とし穴**:
  - **催行回の単独新規作成画面は作らない**（MVP対象外）。新規作成は割り当て時のインライン作成のみ（ハンドオフメモ §2-5）。
  - 候補の絞り込み鍵＝**TourOption ID（TourOptionバージョン）＋ツアー日時＋ゲスト言語の完全一致**（2026-06-15確定。ハンドオフ §3-D）。**「同一TourOption」は「同一TourOption ID（TourOptionバージョン一致）」の意味で、コード一致ではない**（コードは商品系統の不変識別子で、改訂版は同一コードの別ID＝レコード単位で重複しうる）。現行 予約割り当て.html はこのTourOption ID一致ベースで実装されており、プロトタイプと設計仕様は一致する。
  - 同一コード・同一日時・同一言語でも**TourOptionバージョンが異なる回は「同乗不可」として別枠で可視化**（同じ枠に見えるのに紐付けられない理由を運営に提示）。
  - 仮紐付け → 確定紐付け への切替は**催行回詳細**で行う（この画面ではやらない）。

### ② -3. 催行回詳細 / 催行回一覧
- **HTML**: [催行回詳細.html](../催行回詳細.html) / [催行回一覧.html](../催行回一覧.html) ／ **管轄**: 運営管理 §3-5 / §3-6
- **役割**:
  - 催行回詳細＝催行回単位で紐づく予約・ガイド手配・紐付け状況を一覧／操作する詳細ハブ（催行回一覧・当日翌日案件一覧・未手配一覧から遷移）。
  - 催行回一覧＝催行回ごとの人数・手配状況・担当ガイド・催行ステータスを把握。
- **主な機能**:
  - 催行回詳細: ① 基本情報（ID/TourOption/日時/定員・現在人数/催行ステータス/紐付けステータス）② 紐づく予約一覧（各行→予約詳細、グループ仮紐付けは「選択した予約を確定紐付けにする」）③ ガイド手配情報→「手配操作を開く」。
  - **催行回はTourOption ID（TourOptionバージョン）を必須属性で保持**し、この催行回が受け入れるTourOptionバージョンを一意特定する。**紐付く全予約は同一TourOption IDでなければならない（TourOptionバージョン混在禁止）**。基本情報には人間可読の**TourOptionバージョンラベル（連番・発効日。例「v2（2026-05-01〜・現在のTourOptionバージョン）」）を補助表示**（OD-6、現行 催行回詳細.html 反映済み）。定員・最少催行人数は催行回作成時に当該TourOptionバージョンの値をスナップショット（現在のTourOptionバージョンを参照しない）。
  - 催行回一覧: 列＝催行回ID / 日時 / TourOption / 現在人数・定員 / 紐付き予約数 / 催行ステータス / 手配状況 / 担当ガイド。絞り込み＝催行回ID・予約ID・ツアー日・TourOption・催行ステータス・担当ガイド・手配状況・紐付け。
- **落とし穴**: 催行ステータスは **5値（未催行 / Operated / Not Operated / Aborted / Cancelled）**。プロトの催行回詳細.html は3値トグルしかないので実装時は5値に（ハンドオフメモ §3-A）。手配状況は **6ラベル（未手配/募集中/アサイン済み/一部確定/確定済み/要確認）**（§3-B）。

## ③ ガイド手配

> 構成の意図: 手配の前提となる**ガイドマスタ**を先に置く。「誰を」「どこから引いてくるか」を押さえてから手配オペレーション（未手配一覧→手配操作→応募者一覧）に入ると繋がりやすい。

### ③ -1. ガイドマスタ（一覧 → 詳細 → 編集 / 登録）
- **HTML**: [ガイド一覧](../ガイド一覧.html) → [ガイド詳細](../ガイド詳細.html) → [ガイド編集](../ガイド編集.html) / [ガイド登録](../ガイド登録.html) ／ **管轄**: ガイド情報設計資料
- **役割**: 手配対象となるガイドの台帳。
- **主な機能**:
  - ガイド一覧: 検索・絞り込み（対応言語 / エリア / スキルランク / ステータス）。
  - ガイド詳細: 基本情報・**基本時給の履歴**・手配履歴。
  - 登録/編集: ガイド情報フォーム。
- **重要ポイント / 落とし穴**:
  - ガイドID = `G-NNN`（3桁ゼロ埋め、内部IDとコードは1フィールド・変更不可）。
  - 報酬は**基本時給1本**。TourOption別の個別単価マスタは**持たない** → 必要時はアサイン時に「適用時給」を手動上書き（ハンドオフメモ §3-C）。

### ③ -2. 未手配一覧
- **HTML**: [未手配一覧.html](../未手配一覧.html) ／ **管轄**: 運営管理 §3-4
- **役割**: ガイド未アサインの催行回を抽出し、手配漏れを防ぐ。
- **対象条件**: 催行回紐付けが**仮紐付け以上**（未紐付けは除外）かつ手配状況が**未手配 or 要確認**。
- **主な機能**: 催行回単位の表示（グループで複数予約が紐づいても1行）、変更理由区分（要確認の内訳: 日時変更/増員/減員）、各行から手配操作へ。

### ③ -3. ガイド手配操作 ★分岐が肝
- **HTML**: [ガイド手配操作.html](../ガイド手配操作.html) ／ **管轄**: ガイド手配設計資料（画面概要は運営管理 §3-9）
- **役割**: 催行回にガイドをアサインし手配ステータスを進める。
- **主な機能（2経路）**:
  - **直接アサイン**: ガイド検索（エリア=TourOptionエリア / 言語=ゲスト言語で初期フィルタ）→ 役割（メイン/サブ）→ **適用時給を確認・編集（基本時給を初期表示）** → アサイン実行で「アサイン済み」＋アプリ通知 → ガイド確認で「確定」。確認前は解除して差し替え可。
  - **募集**: 言語・エリア条件と締切を設定 → 募集開始で「募集中」＋対象ガイドに通知 → 応募者一覧から選んでアサイン。
  - 再手配: 既存レコードをキャンセルにして新規作成、変更理由区分を記録。
- **重要ポイント**: **適用時給はアサイン時に入力・記録**し、ガイド確認による確定時点で確定値になる（ハンドオフメモ §2-3）。

### ③ -4. 応募者一覧
- **HTML**: [応募者一覧.html](../応募者一覧.html) ／ **管轄**: ガイド手配設計資料
- **役割**: 募集に対する応募を確認し、アサインする（募集経由の手配のゴール地点）。
- **主な機能**: 応募ガイドの一覧・条件確認 → アサイン → 手配ステータス「アサイン済み」へ。

## 横断. 変更・キャンセル処理

### 変更・キャンセル処理
- **HTML**: [変更・キャンセル処理.html](../変更・キャンセル処理.html)
- **資料**: [全条件別フロー（ビジュアル）](../変更・キャンセル_全条件別フロー_ビジュアル.html) ／ **管轄**: 変更・キャンセル設計資料（＋ユースケース・全条件別フロー分析）
- **役割**: 予約詳細から起動し、変更・キャンセルを処理して各所（金額・催行回・ガイド手配）への反映を確定・記録する。
- **主な機能（種別選択 → 専用処理）**:
  - 種別選択: **発生元区分（ゲスト都合 / 運営都合 / 第三者都合）** と変更理由を入力 → 日時変更 / 人数変更 / キャンセル へ分岐。
  - 日時変更: 新日時 → 金額確認（追加請求/差額返金/変更なし）→ 反映（旧催行回無効・新催行回生成・再手配要否フラグON）。
  - 人数変更: 増員/減員を自動判定 → 金額確認 → リソース増減・催行回人数更新・再手配要否フラグON。
  - キャンセル: 内容確認 → 金額確認（キャンセル料率手動入力→料・返金額自動）→ リソース解放・催行回無効化/人数更新・ガイド手配キャンセル。
- **重要ポイント / 落とし穴（事故りやすい）**:
  - **日時変更の受付ゲート**: TourOptionの「日程変更可否」ON **かつ** 無料キャンセル期限内。**ゲスト都合のみ適用**（運営都合・第三者都合は対象外）（ハンドオフメモ §2-2）。
  - **全件キャンセル時のガイド手配**: 催行回の残存有効予約が0件→手配「キャンセル」＋通知要否フラグON。1件以上残る→手配維持＋再手配要否フラグON。**無条件でキャンセルにしない**（ハンドオフメモ §2-1）。
  - 全条件フロー資料（約50パターンの判定ツリー）を併読すると、画面の分岐の根拠が分かる。
